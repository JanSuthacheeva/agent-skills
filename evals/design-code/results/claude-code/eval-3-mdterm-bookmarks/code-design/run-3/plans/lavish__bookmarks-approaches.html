Bookmarks in mdterm - pick an approach

m+letter sets a mark, '+letter jumps to it, marks persist per file across sessions. The real decision is what a "position" is, because that decides which layer owns the mark and what it survives.

What exists today

Position = wrapped-line index

The only notion of "where you are" is ViewerState.offset, an index into wrapped lines viewer.rs:292-294. It changes on every resize viewer.rs:1252-1257, -w, line-number toggle, and when images load and expand viewer.rs:632-657. Lines carry no source position, except task items which record a byte offset style.rs:39-44.

Closest sibling: Backspace history

nav_history: Vec<(usize, usize)> stores (file index, wrapped offset), session-only viewer.rs:364-365, pushed by link-follow viewer.rs:1966, popped by Backspace viewer.rs:1765-1771. Feedback goes through set_toast viewer.rs:454.

Keys: no multi-key sequences yet

All bindings are single keys in handle_normal viewer.rs:1606-1801. Help-toggle (h, ?) is intercepted before mode dispatch viewer.rs:999-1015, slide mode and JSON nav short-circuit first viewer.rs:1610-1617 - a pending m/' must be caught before all of these.

Persistence: read-only config only

Config::load() reads config.toml via dirs::config_dir(), silently falls back to defaults config.rs:29-43. Nothing in mdterm writes state to disk today; no Serialize derive anywhere. The renderer already iterates into_offset_iter() markdown.rs:1585, so source ranges are available for free.

m is already taken - it toggles mouse capture viewer.rs:1647-1663, listed in help viewer.rs:3637. Bookmarks need it moved; my proposal is M (currently unbound). This is a user-visible change, so it is a question in the form below, not an assumption.

A - Viewport marks in ViewerState

Store the wrapped offset, like nav_history

fragile

A mark is the current offset (wrapped-line index). ViewerState holds HashMap<char, usize> for the current file; a new marks.rs only loads/saves them. On load, offsets saved at a different content width are scaled proportionally.

Touches: viewer.rs (state, key handling, help), new marks.rs, main.rs (mod). Fit: mirrors nav_history exactly viewer.rs:365; no renderer change.

Benefits

  • Smallest change; one new file plus viewer edits.
  • Works identically for markdown, JSON and stdin.

Costs

  • Wrong after resize, -w, l, or images loading above the mark - even within one session.
  • Across sessions the terminal size almost always differs; proportional scaling lands "near", not "on".
  • Any edit to the file shifts every mark below it with no way to recover.
  • Persisting a layout artifact means the stored data is wrong by design - hard to fix later without discarding it.

B - Source-anchored marks, renderer stamps source lines

Mark = source line of the block at the top of the viewport

recommended

The renderer stamps each Line with the source line it came from (one place: the into_offset_iter loop, markdown.rs:1585), and wrap_lines carries it through. A new marks.rs owns the per-file mark store (load/save keyed by canonical path) and pure "offset ↔ source line" resolution. viewer.rs only owns the pending-key state and calls into it.

Touches: style.rs (Line field + wrap propagation), markdown.rs (stamping), viewer.rs (pending key, M rebind, help), new marks.rs, main.rs. Fit: same idea as bracket_offset - record the parser's source position at render time style.rs:42, markdown.rs:897; persistence module shaped like config.rs config.rs:29-43.

Benefits

  • Survives resize, -w, line numbers, theme, image loading, slide mode - the anchor is independent of layout.
  • The stored data is meaningful ("line 142 of notes.md"), human-readable, and stays valid across upgrades.
  • marks.rs is pure and unit-testable without a terminal.
  • The source-line stamp is reusable later (e.g. "open in $EDITOR at line", sync scroll after reload).

Costs

  • Touches the core Line type; every Line { .. } literal needs the field (or ..Default::default()).
  • Resolution is block-granular: a mark in the middle of a long paragraph or code block lands on its first line unless we also store a row-within-block.
  • Edits above the mark still shift it by the inserted line count (fixable with a text fingerprint - see questions).
  • JSON view has no source lines; marks there need a fallback or are unsupported.

C - Heading-anchored marks

Mark = nearest heading above + rows below it

A mark stores the slug of the heading owning the viewport top (using the existing toc_entries and heading_to_slug, viewer.rs:847-852, 1918) plus the wrapped-row distance below it. No renderer change; marks.rs owns store and resolution against the TOC.

Touches: viewer.rs, new marks.rs, main.rs. Fit: reuses anchor navigation viewer.rs:1979-1992; no core type change.

Benefits

  • Robust to edits in other sections - lands in the right section after most edits.
  • No change to Line or the renderer.

Costs

  • The row delta is still in wrapped lines, so it drifts on resize - long sections land off-target.
  • Renaming the heading orphans the mark; duplicate headings need an occurrence index.
  • Documents without headings (README fragments, notes) degrade to Approach A.
  • Couples marks to the TOC, which is rebuilt in finalize_layout - ordering subtleties on reload.

Recommendation

B. A persistent mark is only useful if it points at the same content next time, and the next session almost never has the same terminal width - so A stores something that is wrong by design, and C is only partially better. B anchors to the document itself, follows an existing precedent in this codebase (bracket_offset), and keeps the layering clean: the renderer records facts, marks.rs owns persistence and resolution, the viewer only handles keys. The two weak spots (edits shifting lines, block granularity) are addressable inside marks.rs without changing the structure, so they are questions for the implementation page.
