mdterm - code design - phase 2 of 4

Bookmarks: where does a mark point, and who owns it?

Requested: m+letter sets a mark at the current position, '+letter jumps back, marks persist per file between sessions. The approaches below differ in what a stored mark refers to - that single choice decides which modules change and whether a mark still lands in the right place next week.

What exists today

Position is a wrapped-line index

ViewerState.offset indexes wrapped (viewer.rs:292-294). It shifts whenever the content is re-wrapped: terminal resize, l line numbers, image rows growing in finalize_layout (viewer.rs:605-657), and file reloads.

Lines carry no source position

Line { spans, meta } (style.rs:56). The one exception, TaskItem.bracket_offset (style.rs:39-43), proves the renderer can stamp byte offsets: it already iterates into_offset_iter() (markdown.rs:1585).

Keys are single-stroke only

handle_normal matches one KeyCode at a time (viewer.rs:1606-1801); there is no prefix/chord state anywhere. m is taken by mouse-capture toggle (viewer.rs:1647, help entry viewer.rs:3637). ' is free. Slide mode and JSON nav intercept keys first (viewer.rs:1610-1617).

Closest siblings

nav_history: Vec<(file_idx, offset)> + Backspace is an in-session "jump back" (viewer.rs:365, 1765). SearchState is the pattern for a sub-state struct with methods (viewer.rs:2178). config.rs is the only disk I/O: read-only TOML via dirs, silent fallback on error (config.rs:30-43). Nothing writes state to disk yet.

Common to every approach: a new marks.rs owns the persisted store (one JSON file, keyed by canonical file path, serde_json already a dependency), the viewer gets a one-key "pending prefix" state for m/', marks reload on switch_file (viewer.rs:802), and stdin input keeps marks in memory only. These are detailed on the implementation page.

A. Wrapped-offset marks

not recommended

A mark stores offset exactly as the viewer sees it, like nav_history does. Setting is marks.insert(c, state.offset); jumping is clamping the stored number. No renderer change.

Touches

viewer.rs, new marks.rs, main.rs (mod).

Gains

  • Smallest change; mirrors nav_history.
  • No new concept in the render pipeline.

Costs

  • A persisted mark is wrong as soon as the terminal width differs from when it was set - the common case across sessions.
  • Also drifts on l, image load, any edit above it.
  • The stored format would have to be migrated later, so "start simple" is not cheap here.

B. Heading-anchored marks

viable

A mark stores the enclosing heading (slug + occurrence, reusing heading_to_slug, viewer.rs:1918) and how far into that section the view was, as a fraction. Resolving looks the heading up in toc_entries (viewer.rs:661-697). No renderer change.

Touches

viewer.rs, new marks.rs, main.rs (mod). Renderer untouched.

Gains

  • Survives resize roughly and edits in other sections exactly.
  • Stored data is human-readable ("Installation", 40%).

Costs

  • Approximate: a fraction of a section lands a few lines off after resize, more in long sections.
  • Documents without headings fall back to whole-document fraction.
  • Renaming the heading orphans the mark.
  • Fuzzy semantics are hard to test crisply.

C. Source-anchored marks

recommended

The renderer stamps every Line with the source line it came from (same mechanism as bracket_offset), and wrap_lines copies it to continuation lines. A mark stores that source line number plus a short fingerprint of its text. Jumping maps source line to the first wrapped line; if the file was edited, the fingerprint re-locates the line nearby.

Touches

New marks.rs; style.rs (field on Line, ~13 literals), markdown.rs (~15 literals, stamping in flush_line_with_meta), json.rs (~20 literals, default None), viewer.rs.

Gains

  • Exact across resize, l, theme, image loads, width override.
  • Robust to edits via fingerprint; stored line numbers are readable and debuggable.
  • Line.source_line is reusable later (e.g. "open in $EDITOR at line", restoring scroll on reload).
  • Deterministic, unit-testable resolve.

Costs

  • Widest diff: ~50 mechanical Line { .. } literal updates.
  • Granularity is the block's first source line: a mark inside a long wrapped paragraph lands at its top.
  • JSON views have no markdown source; marks there need their own anchor or are unsupported.

Recommendation: C

Persistence is the point of the feature, and what is persisted is the hardest thing to change later. Only C stores a position that means the same thing in the next session regardless of terminal size, and it degrades predictably under edits. The extra cost is mechanical (struct literals), not conceptual, and the new Line.source_line pays for itself beyond bookmarks. B is the fallback if you want the renderer left untouched; A I would not ship because its stored data is wrong in the most common case.
