Bookmarks in mdterm - which structure?

m+letter sets a mark, '+letter jumps to it, and marks persist per file between sessions. The approaches below differ in one structural question: what a "position" is once it has to outlive a terminal resize, an image load or an edit to the file.

What exists today

m is already taken. It toggles mouse capture in Normal mode and is listed in help. src/viewer.rs:1647, src/viewer.rs:3637
A position is a wrapped-line index. ViewerState.offset indexes wrapped, which is re-wrapped at the current content width on every rebuild. src/viewer.rs:294, :575
Image loads shift rows after the first frame. finalize_layout replaces 3-row placeholders with the real height and corrects offset only. src/viewer.rs:605-657
Rendered lines have no source position. Line is { spans, meta }. The only source offset is the TaskItem bracket, taken from into_offset_iter. src/style.rs:55, :39-44; src/markdown.rs:1110, :1585
Key input routes by ViewMode. handle_event dispatches per mode. ? opens help from any mode except text-input modes. src/viewer.rs:229-245, :271, :1062
Closest sibling: nav_history. It stores (file_idx, offset) in memory only. Backspace pops it. src/viewer.rs:365, :1765
Persistence pattern: config.rs. It reads dirs::config_dir()/mdterm/config.toml with serde and falls back to defaults silently. Nothing in mdterm writes state to disk yet. src/config.rs:29-43
Surrounding events: slide mode takes every key (:1610). Auto-reload calls rebuild() (:751). switch_file resets offset (:802). Unit tests live inside the module (:3962).

Shared by every approach

These parts are the same in all three approaches, so the choice below does not depend on them:

  • A new src/marks.rs module owns marks: their in-memory map and their load and save. It follows the shape of config.rs.
  • Pending-key state is a new ViewMode variant, so the second keystroke goes through the normal per-mode dispatch, and ?/h are not swallowed as help toggles.
  • Feedback goes through the existing toast (set_toast, src/viewer.rs:454).

A. Source-anchored marks recommended

The renderer stamps each Line with the source line it came from, and wrap_lines carries that stamp onto every wrapped row. A mark stores the source line number (plus the row within that block). Jumping looks that line up in the current wrapped. Width, theme, line numbers and image heights stop mattering because none of them change source lines.

Touches: new src/marks.rs. Modified: src/style.rs (field on Line, propagation in wrap_lines), src/markdown.rs (one stamping point in the into_offset_iter loop, :1585), src/viewer.rs (mode, keys, help), README.

Benefits

  • Marks are correct across resize, --width, line-number toggles and late image loads, both within a session and between sessions.
  • A mark means something to people: "line 42" can go in the toast and in the stored file.
  • Follows the precedent of TaskItem.bracket_offset: the renderer already threads source offsets into line metadata.
  • The source line on Line can be reused later (for example "open in $EDITOR at this line").

Costs

  • About 50 mechanical edits where Line { .. } is built as a literal (json.rs 20, markdown.rs 15, style.rs 13, viewer.rs 3), or a switch to a constructor.
  • Marks land on the first row of a block. Inside a long wrapped paragraph that needs a row delta, which is clamped after a resize.
  • Edits above a mark shift it by the number of inserted lines, unless we re-anchor (question 3 below).
  • JSON views have no source lines. They need a fallback or no marks at all.

B. Heading-anchored marks

The renderer is left alone. A mark stores the nearest heading above the viewport (its slug and which occurrence it is) plus how many wrapped rows below that heading the viewport was. Jumping resolves the heading through toc_entries, the same way navigate_to_anchor does (src/viewer.rs:1979), then adds the delta.

Touches: new src/marks.rs, src/viewer.rs, README. The rendering pipeline is unchanged.

Benefits

  • Smallest diff. style.rs and markdown.rs are untouched.
  • A mark survives edits outside its section, and the heading itself can move anywhere.

Costs

  • The delta is in wrapped rows, so a resize moves the mark inside a long section. That is the exact failure we want to avoid.
  • Late image loads inside the section still shift it, so it is wrong even within one session.
  • Renaming the heading orphans the mark. Documents without headings need a separate fallback.
  • Two ways of resolving a position mean two sets of edge cases.

C. Raw viewport offset rejected

A mark stores state.offset as it is, the same way nav_history does. This is the obvious first idea, so it is shown here to make clear why it is rejected.

Benefits

  • About 20 lines of new state, plus the store.

Costs

  • Wrong after any change of width, so in practice wrong in every new session.
  • Wrong within a session when images finish loading, because finalize_layout corrects offset but no other stored indices (:657).
  • Toggling line numbers changes the wrapped row count, so it breaks marks too.

Recommendation

A, source-anchored. Persistence only makes sense if a stored mark lands in the same place after the terminal changes size, and only a source anchor gives that. The extra cost is a mechanical field addition, and the codebase already threads a source offset through TaskItem. Add text re-anchoring (Q3) to deal with edits, because mdterm auto-reloads while you edit.
