Bounded change Approved 2026-10-01

Design: clickup tasks status <id> <status>

Change a task's status from the CLI. The new status is checked against the task's own list, and if it doesn't match, the valid statuses are shown and nothing changes.

Agreed decisions

Matching
Exact match, ignoring case. Leading and trailing spaces are trimmed. No prefix matching.
Invalid status
Exits non-zero, makes no update call, and lists the valid statuses in list order.
Canonical name
Sends ClickUp's spelling of the status, not what you typed.
Same status
Prints a note, exits 0, and makes no update call.
Success output
One line: HGAI-1217: in progress -> review
Docs
README.md and skills/SKILL.md get the new command.

How a status change runs

Three API calls. The status is checked locally between the second and third, so a bad name never reaches the update call.

Calls 1 and 4 add custom_task_ids=true&team_id=… for custom IDs like HGAI-1217, the same way GetTask already does (internal/api/tasks.go:67). GET /list returns the statuses the list actually uses, including ones inherited from its folder or space.

What you'll see

clickup tasks status HGAI-1217 Review
HGAI-1217: in progress -> review
 
clickup tasks status HGAI-1217 review
HGAI-1217 is already review
 
clickup tasks status HGAI-1217 rev
Error: invalid status "rev" for list "Sprint 12"
Valid statuses:
  to do
  in progress
  review
  complete

Multi-word statuses need quotes ("in progress"). Because of cobra.ExactArgs(2), leaving the quotes off gives an argument-count error, so it can't silently match the wrong status.

Separate fix: debug output (approved)

--debug prints to stdout (internal/api/client.go:49,72,74). That breaks --output json and would mix into the new success line. It moves to stderr, as its own commit.

Risks

A task whose ID is literally status can't be viewed with tasks status. Real IDs never look like that. The --status filter flag and the status subcommand have similar names, so the help examples show both side by side.
