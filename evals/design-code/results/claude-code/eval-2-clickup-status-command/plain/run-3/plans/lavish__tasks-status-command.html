Implementation plan

clickup tasks status <id> <status>

Change a task's status from the terminal. The requested status is validated against the statuses of the task's home list; a wrong value fails before any write and prints the valid statuses in workflow order.

Valid status

$ clickup tasks status HGAI-1217 review HGAI-1217: in progress -> review $ clickup tasks status HGAI-1217 In Progress HGAI-1217: review -> in progress

Invalid status

$ clickup tasks status HGAI-1217 revew Error: invalid status "revew" for list "Sprint 42" Valid statuses: to do, in progress, review, complete # exit 1, no PUT sent

Current state (verified in code)

  • client.goOnly Get exists; doRequest(method, path, query) cannot send a body.
  • tasks.go / comments.goCustom task ID query logic (custom_task_ids + team_id) is duplicated.

Flow

sequenceDiagram
  participant U as User
  participant C as tasks status
  participant API as ClickUp API
  U->>C: status HGAI-1217 review
  C->>API: GET /task/HGAI-1217?custom_task_ids&team_id
  API-->>C: task (status, list.id)
  C->>API: GET /list/{list.id}
  API-->>C: list (name, statuses[])
  alt no case-insensitive match
    C-->>U: error + valid statuses (exit 1)
  else already in that status
    C-->>U: already "review" (exit 0, no write)
  else match
    C->>API: PUT /task/HGAI-1217 {"status":"review"}
    API-->>C: updated task
    C-->>U: HGAI-1217: in progress -> review
  end

The canonical name from the list is sent, not raw input. GET /list returns effective statuses, so folder/space inheritance is resolved by ClickUp.

Key decisions

Cobra subcommand of tasks

Cobra matches subcommand names before the parent's positional arg, and the parent has explicit Args, so clickup tasks HGAI-1217 keeps working. Parent flags are local and don't leak.

Validate client-side, before write

Lets us show the valid list in workflow order and a clear message, instead of relaying ClickUp's opaque 400. Costs one extra GET.

Unquoted multi-word status

MinimumNArgs(2), status = strings.Join(args[1:], " "). ID is always first, so it's unambiguous. Quoting still works.

Risks and edge cases

No access to list (GET /list 401)Wrap: failed to load statuses for list "...".

3 requests per changeNegligible for an interactive command; no caching.

Decisions approved

1. Unquoted multi-word statuses are accepted (status X in progress).
2. No "did you mean" suggestion for now - the full valid list is shown instead.
3. Success output is one line ID: old -> new; -o json prints the updated task.
