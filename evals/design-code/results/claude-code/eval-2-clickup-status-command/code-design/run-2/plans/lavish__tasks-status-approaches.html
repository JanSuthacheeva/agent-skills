Where should the status-change logic live?

Feature: clickup tasks status <id> <status> changes a task's status, validates the target against the statuses of the task's list, and lists the valid ones when the target is wrong. Pick one structure below; signatures and call chains follow on the implementation page.

new modified existing

What exists today

  • tasks is a single Cobra command tasks [task_id] with MaximumNArgs(1) and no subcommands; flags are package-level vars - internal/commands/tasks.go:15-50. Commands self-register in init().
  • Command functions fetch getAPIClient() + getConfig(), call the client, wrap errors as fmt.Errorf("failed to ...: %w", err), and print via output.GetFormatter - tasks.go:100-159. Execute() prints Error: ... to stderr and exits 1 - root.go:48-53.
  • The API client is read-only: doRequest(method, path, query) sends no body and only Get is exposed - internal/api/client.go:42-96. Each client method maps one endpoint to one model (api/tasks.go:59, api/comments.go:13). Non-2xx becomes *APIError - api/errors.go:8.
  • Custom IDs like HGAI-1217 need custom_task_ids=true&team_id=...; detected by isCustomTaskID - api/tasks.go:66-70, 88.
  • models.Task already has Status and List ListInfo{ID, Name}, but there is no model for a list or its statuses - pkg/models/task.go:16, 26, 55, 80.
  • Tests exist for models and formatters only; there are no API client tests and no command tests - pkg/models/task_test.go, internal/output/table_test.go.
All approaches share the same base needs: a body-capable doRequest + Put, GET /list/{id} (returns statuses[]), PUT /task/{id} with {"status": ...}, and a status subcommand under tasksCmd. Cobra still routes clickup tasks HGAI-1217 to the parent since non-root commands only match subcommands by name. They differ in who owns validation and when it runs.

A - Command orchestrates, model validates

recommended

The new subcommand fetches the task, fetches its list, asks the list model whether the requested status exists, and only then writes. The API client stays a thin one-endpoint-per-method mapping; the matching rule is a pure method on a new models.List.

Touches

  • new commands/tasks_status.go
  • new api/lists.go, models/list.go
  • api/tasks.go (+UpdateTaskStatus)
  • api/client.go (body, Put)
  • README, skills/SKILL.md

Benefits

  • Mirrors getTask: command orchestrates several client calls (tasks.go:111-124)
  • Keeps client 1 method = 1 endpoint (api/tasks.go:59)
  • Validation is a pure function - unit-testable like task_test.go with no HTTP
  • Can normalize case before writing and skip a no-op write

Costs

  • 3 round trips on every change (GET task, GET list, PUT)
  • Orchestration lives in the command, which has no test seam today - covered only by E2E
  • Small TOCTOU window if the list's statuses change between GET and PUT (API still rejects)

B - API client owns the whole operation

A single Client.SetTaskStatus(taskID, teamID, status) does the GET task, GET list, validation and PUT internally, returning a typed *InvalidStatusError{Valid []Status}. The command just calls it and formats the result.

Touches

  • same files as A
  • + api/errors.go (new error type)
  • logic moves from commands to api

Benefits

  • Thinnest command
  • Operation reusable if another command (e.g. a future tasks close) needs it

Costs

  • Breaks the api package's role as a transport mapping - first method that composes calls and applies business rules
  • Testing needs an httptest server; none exists yet
  • Hides 3 HTTP calls behind one innocent-looking method

C - Optimistic write, explain on failure

The command sends the PUT straight away. Only if ClickUp rejects it as an unknown status does it fetch the task and its list to print the valid statuses. No pre-validation.

Touches

  • same files as A
  • + classification of *APIError by ECODE

Benefits

  • 1 round trip on the happy path
  • ClickUp stays the single source of truth

Costs

  • Depends on ClickUp's undocumented error code for "status not found" - silent breakage if it changes
  • Cannot normalize input (case) or detect no-ops before writing
  • Error path is the complex path - hardest to test

Recommendation: A

A follows the codebase's existing split exactly: commands orchestrate (tasks.go:111-124 already chains two GetTask calls), the client maps endpoints, and models hold pure helpers (task.go:36-52). The validation rule ends up as the most testable piece instead of the least. Two extra GETs are negligible for an interactive command, and it does not rely on an undocumented error code. B is worth revisiting only once a second command needs the same composed operation.
