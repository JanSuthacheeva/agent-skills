Code design - phase 2

Where does the status change live?

Adding clickup tasks status <id> <status>. It changes a task's status, checks the new status against the statuses of the task's list, and lists the valid ones when the status is wrong. The approaches below differ in which layer owns the "fetch task, fetch list, validate, update" flow.

Prerequisite, unrelated to this feature: main does not compile. DetailFormatter.FormatComments is declared twice (internal/output/table.go:191 and :238, from the word-wrap commit). Every approach starts with a separate commit that deletes the older, non-wrapping copy at :238.

What exists today

  • Commands orchestrate. getTask calls client.GetTask, then makes a second GetTask call for the parent, then formats the output. Any multi-call flow lives in the command layer (internal/commands/tasks.go:100-159).
  • The API client is a thin wrapper. Each method builds a path and query, calls c.Get and unmarshals the response into a model (internal/api/tasks.go:59-83, comments.go:13-33). The client has no domain rules.
  • The client can only send GET requests. doRequest(method, path, query) sends a nil body (internal/api/client.go:42,52), so a PUT needs a request body to be added.
  • Custom task IDs (HGAI-1217) need custom_task_ids=true&team_id=.... isCustomTaskID handles this and is reused per endpoint (tasks.go:67-70,88).
  • Models already have Status (pkg/models/task.go:55) and Task.List ListInfo (id and name only, :79). Nothing models a list's status set yet.
  • Command tree: tasks [task_id] uses cobra.MaximumNArgs(1) (tasks.go:25,37). Cobra routes tasks status ... to a child command before positional args are handled, so tasks <id> keeps working.
  • Errors: commands wrap with fmt.Errorf("failed to ...: %w"), and Execute prints Error: ... to stderr and exits with code 1 (root.go:48-53). APIError is the only typed error (api/errors.go).
  • Tests exist only for models, output and config (pkg/models/task_test.go, internal/output/table_test.go). Nothing tests api or commands.

A - Command orchestrates, thin API methods, matching on the model

Recommended

A new tasks status subcommand fetches the task, then its list, and asks List.FindStatus for a case-insensitive match. On a match it calls UpdateTaskStatus; otherwise it returns an error that lists the valid statuses. The API gets two thin methods and a Put, like the existing ones. The command layer orchestrates the calls, as getTask already does.

Touches

  • new internal/commands/tasks_status.go
  • new internal/api/lists.go (GetList)
  • internal/api/tasks.go (+UpdateTaskStatus)
  • internal/api/client.go (body + Put)
  • new pkg/models/list.go (List, FindStatus)
  • skills/SKILL.md, README.md

Fit

  • Uses the same orchestration pattern as getTask (tasks.go:100-124).
  • New API methods follow GetTask/GetTaskComments exactly.
  • Domain helper on the model, like Task.GetDisplayID (task.go:36).
  • Puts each domain file in its own file, like comments.go/user.go.
Gains
  • The matching rule is a pure function on models.List that you can unit test with no HTTP.
  • Every API method stays a 1:1 endpoint wrapper, so it can be reused later (for example to validate --status on list).
  • No new error types.
Costs
  • Makes 3 HTTP calls per change (GET task, GET list, PUT).
  • The command function holds the flow. Like the rest of commands, it has no automated test without an HTTP fake, so the flow is only covered manually or end to end.

B - API client owns the whole operation

A single client.SetTaskStatus(taskID, teamID, status) fetches the task and its list, validates the status, and sends the PUT. A wrong status comes back as a typed *InvalidStatusError{Requested, Valid []models.Status}. The command only parses args, calls this method, and formats the result or the error.

Gains
  • One call from the command, so any future caller (another command, a TUI) gets validation for free.
  • The error type carries data and the command decides how to show it.
Costs
  • Breaks the current split, because api would gain domain rules. Today it is a thin wrapper and orchestration lives in commands (tasks.go:117-124).
  • Adds a second error type next to APIError, and callers must type-assert it.
  • Testing the validation means faking HTTP, because the rule sits behind network calls.
  • Adds the most new code for one caller.

C - Send the update first, explain only when it fails

The command sends the PUT straight away. Only if ClickUp rejects it as an unknown status does the command fetch the task and its list and print the valid statuses. The happy path needs a single request.

Gains
  • Only 1 request on the happy path.
  • ClickUp stays the only source of truth, so there is no local matching rule to drift.
Costs
  • Depends on telling an "unknown status" 400 apart from other 400s by ClickUp's err/ECODE text. That text is undocumented and not verified, and it can change without notice.
  • ClickUp's own matching (case, whitespace) decides what is accepted, so we cannot normalise input or show a hint before the write.
  • The task gets mutated before we know the input was good. That is harmless here, but it is the wrong order for a validating command.

Recommendation: A

A copies the split the codebase already uses: commands orchestrate, the API wraps endpoints, and models carry small helpers. The only real rule, matching a typed status against the list's statuses, ends up as a pure function that is easy to test. B pays for reuse that has no second caller. C swaps a stable flow for parsing undocumented ClickUp error text. The extra GET in A takes about 100-200 ms on an interactive command.

Questions about the public surface (how multi-word statuses are passed, how strict matching is, what success prints) do not change which approach fits. They come as open questions on the implementation page.
