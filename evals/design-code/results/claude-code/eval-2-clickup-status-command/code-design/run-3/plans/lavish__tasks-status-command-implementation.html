1. Decision recap

A new status subcommand of tasks coordinates the flow the same way getTask does: get the task, get its home list, match the requested name with models.List.FindStatus, then PUT the canonical name. The API client gains write support and two thin endpoint methods. The only real logic is pure model code.

Decided in phase 2: Approach A. Validation happens before the write, the coordination lives in the command layer, and no service layer is added.

Step 0 of the implementation: delete the duplicate DetailFormatter.FormatComments at internal/output/table.go:237-279 (the older copy, without word wrapping). Until then the package does not compile.

2. Structure overview

new modified existing / external

output/table.go isn't part of the feature. It's on the diagram because the build must be fixed first. Nothing goes through the Formatter interface (see Conventions).

3. Units

internal/commands/tasks_status.go

newcommands

Responsibility: turn tasks status <id> <status> into a validated status change and report the outcome.

Collaborators: getAPIClient(), getConfig() (root.go), *api.Client, *models.List. Registers itself on tasksCmd in init().

  • runTasksStatus - RunE. Fetches the task and its list, validates, updates, and prints one line. Returns a wrapped error on any failure (step list in section 5).
  • invalidStatusError - builds the multi-line error that lists the list's statuses in board order and marks the current one. Pure, so it can be unit-tested.

pkg/models/list.go

newmodels

Responsibility: represent a ClickUp list and answer questions about its statuses.

Collaborators: none (uses existing models.Status).

  • FindStatus - returns the list's own *Status (canonical casing) and true, or nil, false. Matching ignores case and surrounding whitespace. No prefix or fuzzy matching.
  • StatusNames - status names sorted by Orderindex, i.e. the board's column order.

internal/api/lists.go

newapi

Responsibility: fetch a list from GET /list/{list_id}.

Collaborators: Client.Get.

GetList returns *models.List, or the *APIError from doRequest unchanged, or a JSON decode error.

internal/api/tasks.go

modifiedapi

Responsibility (added): update a task's status with PUT /task/{task_id}.

Collaborators: Client.Put.

  • UpdateTaskStatus - sends {"status": status} and returns the updated *models.Task that ClickUp sends back. Errors are the same as GetList's.
  • setCustomTaskIDParams - extracts the custom-ID query logic that currently appears in GetTask (tasks.go:66-70) and GetTaskComments (comments.go:17-20), so it isn't duplicated a third time. Both existing call sites switch to it. Their behaviour doesn't change.

internal/api/client.go

modifiedapi

Responsibility (unchanged): perform authenticated HTTP requests against the ClickUp API.

  • doRequest - gains a body interface{} parameter. A nil body sends no request body, as today. A non-nil body is JSON-marshalled, and in --debug mode it's logged next to the URL.
  • Get - now passes nil as the body. Its signature doesn't change.
  • Put - new. Same return contract as Get.

Help text and docs

modified
  • internal/commands/tasks.go - tasksCmd.Long examples gain clickup tasks status HGAI-1217 "in progress" Change task status.
  • internal/commands/root.go - rootCmd.Long "Get started" gains clickup tasks status <ID> <status>.
  • README.md, skills/SKILL.md - a usage line next to the existing --status filter example.

5. Call chain - clickup tasks status HGAI-1217 "in progress"

  1. rootCmd.Execute -> tasksStatusCmd.RunE runTasksStatus(cmd, args): error. Cobra rejects anything other than exactly 2 args first: Error: accepts 2 arg(s), received 1.
  2. runTasksStatus -> getAPIClient(): (*api.Client, error). A config error is returned unchanged, same as getTask.
  3. runTasksStatus -> getConfig(): (*config.Config, error)
  4. runTasksStatus -> Client::GetTask(taskID, cfg.WorkspaceID): (*models.Task, error) -> Get("/task/{id}"). On error: fmt.Errorf("failed to get task: %w", err) -> Error: failed to get task: API error (status 404): ...
  5. runTasksStatus -> Client::GetList(task.List.ID): (*models.List, error) -> Get("/list/{id}"). On error: "failed to get list statuses: %w".
  6. runTasksStatus -> List::FindStatus(args[1]): (*models.Status, bool). On false: return invalidStatusError(args[1], task, list). Nothing is written, and the user sees the valid statuses (see below). Exit 1.
  7. If strings.EqualFold(status.Status, task.Status.Status): print HGAI-1217 is already in progress, return nil, and skip the PUT.
  8. runTasksStatus -> Client::UpdateTaskStatus(taskID, cfg.WorkspaceID, status.Status): (*models.Task, error) -> Put("/task/{id}", query, updateTaskRequest{Status}) -> doRequest(PUT, ..., body). On error: "failed to update task status: %w".
  9. runTasksStatus -> fmt.Printf("%s: %s -> %s\n", updated.GetDisplayID(), task.Status.Status, updated.Status.Status), return nil.

Deviations

  • Output bypasses output.Formatter. The interface only covers tasks and comments (formatter.go:17-24). Adding a confirmation method would mean three implementations for one line of text. Printing directly with fmt.Printf matches the existing "Opened in browser" line (tasks.go:130).
  • doRequest signature changes. It's private and has only one caller (Get), so nothing outside the package is affected.
  • First HTTP-level tests in internal/api, using httptest. Being in the same package lets them set the unexported baseURL, so no new constructor option is needed.

7. Test seams

  • models.List (list_test.go) - unit. FindStatus exact, different case, padded, missing and empty-list cases. StatusNames ordering by Orderindex. Decoding a recorded GET /list payload. No fakes.
  • invalidStatusError (commands/tasks_status_test.go) - unit on the message: the valid names in board order and the (current) marker.
  • Client.GetList, Client.UpdateTaskStatus, Put (api/*_test.go) - an httptest.Server stands in for ClickUp. Assert the method, path, custom-ID query and JSON body, and that a 4xx comes back as *APIError.
  • runTasksStatus - no unit test, same as getTask. Verified E2E with the built binary against a real workspace: success, different case, invalid name, already in that status, unknown task ID, and a custom ID versus a native ID.

8. Assumptions

  1. Matching is case-insensitive and whitespace-trimmed, with no prefix or fuzzy matching. The list's canonical name is what gets sent.
  2. Validation uses the task's home list (task.List), whose statuses ClickUp applies to the task.
  3. Closed-type statuses (e.g. complete) are allowed like any other status.
  4. Valid statuses are listed in board order (Orderindex), one per line, with the current one marked (current).
  5. An invalid status goes through the normal error path: stderr, exit 1, nothing written.
  6. There's no --output flag on status, and the confirmation is one plain line. A JSON flag can be added later without breaking anything.
  7. --debug also logs the JSON request body.
  8. The custom-ID query logic moves into setCustomTaskIDParams, used by all three task endpoints.

9. Decisions made in review

  • Success output: one line, HGAI-1217: to do -> in progress.
  • Task already has that status: skip the PUT, print HGAI-1217 is already review, exit 0.
  • Multi-word statuses: must be quoted. The command uses cobra.ExactArgs(2).
