# Fix: tagging one bookmark tags all bookmarks that have no tags yet

Report: SHOP-313 "Tagging one bookmark tags all of them"

## Report

Expected: `bm tag 3 recipes` tags only bookmark 3.
Actual: `bm list --tag recipes` lists every bookmark.
Steps and environment: after updating bm, `bm tag 3 recipes`, then `bm list --tag recipes` shows all 40 bookmarks. The reporter guesses the tag command ignores the id (it does not).

## Reproduction

Setup: a bookmarks file written before tags existed (records have no `tags` key).

    export BM_FILE=$(mktemp -d)/b.json
    cat > $BM_FILE <<'EOF'
    [{"id":1,"url":"http://a","title":"a","createdAt":"2026-01-01T00:00:00.000Z"},
     {"id":2,"url":"http://b","title":"b","createdAt":"2026-01-01T00:00:00.000Z"},
     {"id":3,"url":"http://c","title":"c","createdAt":"2026-01-01T00:00:00.000Z"}]
    EOF
    npm run -s bm -- tag 3 recipes
    # tagged 3 recipes
    npm run -s bm -- list --tag recipes
    # 1  a  http://a
    # 2  b  http://b
    # 3  c  http://c
    grep -c recipes $BM_FILE
    # 3

Fails every run. Control: bookmarks created with `bm add` on a fresh file
(`add` x2, `tag 1 foo`, `list --tag foo`) list only bookmark 1.

## Root cause

`src/store.ts:21` defines one module-level array `noTags`, and
`fromRecord()` (`src/store.ts:36`) gives that same array to every record
without a `tags` key (`record.tags ?? noTags`). `BookmarkStore.tag()`
(`src/store.ts:73`) then does `bookmark.tags.push(...)`, which mutates the
shared array, so all legacy bookmarks get the tag, and `save()` writes it
into each record. Bookmarks created after the tags commit have their own
`tags: []`, so only users with older data are hit (matches "since I
updated"). Proven by the reproduction: legacy file shows the tag on all
three records, fresh `add`-created file does not. Introduced in 431d4f7
"bm: tag bookmarks and list by tag".

## Fix

In `fromRecord()`, return a fresh array per bookmark: `tags: record.tags ?? []`
(or `[...record.tags]`), and delete the `noTags` constant. No signature
changes. Fixed at the load boundary, so no reader can mutate shared state,
rather than copying inside `tag()`.

## Also affected

Data already damaged: any bookmarks file where a legacy (tag-less) bookmark
was tagged now has that tag written on every legacy bookmark. The fix
does not repair it, and the files cannot tell wrongly applied tags from
real ones. No other uses of `noTags` found.

## Assumptions

- The regression test goes in `test/store.tags.test.ts`, using a file
  without `tags` keys.

## Open questions

1. Repair already-damaged files? - recommended: no automatic repair (the
   wrong tags are indistinguishable from intended ones); tell the reporter
   to remove the wrong tags by hand, and mention it in the release notes.
   There is no untag command; adding one is a public-surface change, so
   only on request.

## Tasks

- [ ] Add "tagging one legacy bookmark leaves the others untagged" in
  `test/store.tags.test.ts` (load a file with two records lacking `tags`,
  `tag(1, 'x')`, expect `listTagged('x')` to have length 1; fails today with
  `2 !== 1`), then fix `fromRecord()` in `src/store.ts`
- [ ] End-to-end: run the reproduction again and see only `3  c  http://c`
  from `list --tag recipes`, and `grep -c recipes` print `1`
