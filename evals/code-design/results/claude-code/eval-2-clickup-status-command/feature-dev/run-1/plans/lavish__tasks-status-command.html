Implementation plan clickup-cli Go / Cobra

clickup tasks status <id> <status>

Change a task's status from the CLI. The command checks the requested status against the statuses of the task's list. If it isn't valid, the command fails and lists the valid ones in board order.

Confirmed decisions

MatchingCase-insensitive exact match on the trimmed input. No prefix matching.
Invalid statusExit 1. List statuses in board order (orderindex) and mark the current one. No color.
Already in statusSkip the API call, print a notice, exit 0.
Success outputOne line: HGAI-1217: to do -> in progress. With -o json, print the updated task.
ArgumentsExactly 2. Quote multi-word statuses.
ConfirmationNone.
ScopeNo statuses listing command. Refresh bin/ with make build-all.

Behavior

Each example starts from the same state: HGAI-1217 is in to do on list "Sprint 42".

Success - mixed case input
$ clickup tasks status HGAI-1217 "In Progress" HGAI-1217: to do -> in progress
Invalid status - exit 1
$ clickup tasks status HGAI-1217 doing Error: "doing" is not a valid status for list "Sprint 42". Valid statuses: to do (current) in progress review complete
Already in status - exit 0, no PUT
$ clickup tasks status HGAI-1217 "To Do" HGAI-1217 is already "to do"
JSON - stdout is task JSON only
$ clickup tasks status HGAI-1217 review -o json { "id": "86a3xyzw", "custom_id": "HGAI-1217", "status": { "status": "review", ... }, ... }

With -o json, stdout contains only task JSON. In the "already" case that's the unchanged task, and the notice goes to stderr.

How a status change runs

Three API calls at most. Validation happens before any write, and the PUT sends the list's own spelling of the status, never the user's input.

Decision: where should the logic live?

A. Minimal

Everything goes inline in the command. The API gets GetListStatuses + UpdateTaskStatus. No refactors.

+ Fewest lines touched
- Matching can only be tested through HTTP
- A 3rd copy of the custom-ID query
- No command-level test possible

B. Layered

Chosen

The model owns matching. The client gets generic body support plus thin GetList / UpdateTaskStatus. The command orchestrates and formats output.

+ Each layer does one thing
+ Matching is unit-tested, and the full flow is tested against httptest
+ Follows the per-domain file pattern in internal/api
- About twice A's diff, and touches client.go

C. API service method

Client.SetTaskStatus does get, validate and update, and returns a typed InvalidStatusError.

+ One call for future callers
- Puts business rules into a thin HTTP transport
- Hides the 3 round trips
- The "already" case and output decisions still end up back in the command

Chosen: B (approved). it's the simplest design where every piece is testable and nothing sits in the wrong layer. A saves a few lines but gives up testability. C builds an abstraction for a single caller. The rest of this plan assumes B.

Manual end-to-end check against a real workspace

  1. A valid change, once with a native ID and once with a custom ID.
  2. Mixed-case input.
  3. An invalid status: the order matches the ClickUp board and the current status is marked.
  4. The same status: a notice, and no entry in the ClickUp activity log.
  5. A subtask.
  6. A list that inherits statuses from its folder or space (see risks).
  7. -o json and --debug -o json | jq .
  8. Regressions: clickup tasks, clickup tasks HGAI-1217, clickup tasks --status open.

Risks

verifyInherited statuses. GET /list/{id} should return the list's effective statuses even when they're inherited from the folder or space. The empty-statuses guard and E2E step 6 cover this. If it turns out to be wrong, fall back to GET /folder and then GET /space, but only if the check shows it's needed.
acceptedThree round trips. GetTask also fetches subtasks and the markdown description, which this command doesn't use. That's fine for an interactive command.
acceptedConcurrent status edits. If someone changes the list's statuses between validation and the PUT, ClickUp rejects the PUT and the error shows as failed to update status: ....
acceptedstatus becomes reserved under tasks. A task with the literal ID status could no longer be viewed. ClickUp IDs never look like that.
intended--output becomes a persistent flag. It shows up under "Global Flags" in tasks status --help.
