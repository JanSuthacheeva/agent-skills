Implementation plan clickup-cli Approved - approach B

clickup tasks status <id> [status]

Change a task's status from the CLI, validated against the statuses of the task's list. With no status given, print the valid statuses.

What the user sees

Change status
$ clickup tasks status HGAI-1217 "in review" HGAI-1217: to do -> in review
List valid statuses (no status argument)
$ clickup tasks status HGAI-1217 to do (current) in progress in review complete
Invalid status - stderr, exit 1
$ clickup tasks status HGAI-1217 reveiw Error: invalid status "reveiw" for list "Sprint 12". Valid statuses: to do (current) in progress in review complete
Already in that status - no PUT, exit 0
$ clickup tasks status HGAI-1217 "In Review" HGAI-1217 is already "in review"
List valid statuses as JSON - array of names in board order
$ clickup tasks status HGAI-1217 -o json [ "to do", "in progress", "in review", "complete" ]

Statuses are listed in board order (orderindex), names only. With -o json, a successful change prints the updated task returned by the PUT.

Current state (verified)

main does not compile. DetailFormatter.FormatComments is declared twice in internal/output/table.go (lines 191 and 238), left over from merge 7411557. The second copy is the old one without word wrapping. This is fixed first.

Command routing

tasksCmd is tasks [task_id] with MaximumNArgs(1) (internal/commands/tasks.go:24). Cobra matches a status subcommand before it checks the parent's arguments, so tasks <id> keeps working, and the task/t aliases still apply.

API client

doRequest (internal/api/client.go:42) always sends a nil body, and only Get exists. The custom-ID query is duplicated in GetTask and GetTaskComments.

Models

Task.List.ID is already returned by GetTask. models.Status exists; there's no list model with statuses.

ClickUp API (developer.clickup.com)

GET /list/{id} returns statuses[] with status, orderindex, color, type. PUT /task/{id} takes {"status": "..."} plus custom_task_ids/team_id and returns the updated task.

Flow

This is how one invocation turns into API calls: 3 calls on the change path, and 2 when it only lists or when there is nothing to change.

Approaches

A. Minimal

Everything goes in the command file: an inline map body, a string-built list, an EqualFold loop.

+ Fewest files
- Logic can't be tested without the CLI
- Output formatting ends up in commands

B. Layered

Recommended

API methods in api, lookup and ordering on models.List, rendering in output, and a thin command.

+ Each layer can be unit tested
+ Matches the package layout in CLAUDE.md
+ TaskUpdate has room for more fields later

C. Status cache

Cache each list's statuses in config to save one call.

- Stale cache when statuses are edited in ClickUp
- Invalidation logic to save one request

Risks

Inherited statuses. Lists that don't override statuses inherit them from the folder or space. The docs show GET /list returns the effective set; the E2E run includes such a list.
Tasks in multiple lists. task.list is the home list, and its statuses are the ones that govern the task.
Race. A status deleted between the GET and the PUT shows up as an API error. Acceptable.
Test isolation. Cobra flag values persist on the package-level rootCmd, so each test resets the flags it sets.
