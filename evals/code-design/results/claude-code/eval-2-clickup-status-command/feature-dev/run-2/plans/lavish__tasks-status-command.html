clickup tasks status <id> <status>

Change a task's status from the CLI. The status is checked against the task's home list before anything is written. If it does not match, the command lists the valid statuses.

Target behavior

Valid status (any casing)

$ clickup tasks status HGAI-1217 "In Progress" HGAI-1217: to do -> in progress

Already in that status - no write, exit 0

$ clickup tasks status HGAI-1217 "in progress" HGAI-1217 is already "in progress"

Invalid status - no write, stderr, exit 1

$ clickup tasks status HGAI-1217 done Error: invalid status "done" for list "Sprint 12". Valid statuses: to do in progress (current) review complete

For scripts and the Claude skill

$ clickup tasks status HGAI-1217 review --output json { ...updated task returned by the PUT... } $ clickup tasks status HGAI-1217 review --output json # already "review" { ...task from the initial GET /task - no PUT is sent... }

Both cases print a models.Task, so the shape matches. The GET version also fills subtasks and markdown_description, because GetTask requests them.

Current state

The build is broken on main. Merge commit 7411557 left two copies of DetailFormatter.FormatComments in internal/output/table.go (lines 191 and 238). go build ./..., make check and the output tests fail.
  • tasksCmd is tasks [task_id] with only local flags. A status subcommand gets the arguments when the first arg is status, and tasks HGAI-1217 keeps working. The only collision is a task whose ID is literally "status".
  • api.Client.doRequest only sends GET requests with no body. [DEBUG] output goes to stdout and corrupts --output json.
  • The custom_task_ids/team_id query is duplicated in GetTask and GetTaskComments.
  • models.Task.List.ID already exists. models.Status has the same shape as the list's statuses[] entries. There is no List model yet.
  • There are no HTTP-level tests. baseURL exists but is unexported.

Request flow

Three calls on the success path. Both failure checks run before the PUT, so nothing is written when validation fails.

Approach

A - Inline in tasks.go

An ad-hoc map[string]any body and a raw list fetch inside the command.

+ smallest diff

- the command does API and domain work, the request is an untyped bag, and nothing can be tested without the network

B - Layered Chosen

The API layer gets typed methods, the model owns status lookup, and the command orchestrates and renders.

+ follows the existing api / models / commands split, and tests run through the real HTTP path via httptest

- about 8 files touched

C - Interface + mocks

A TaskService interface in commands with a mock in tests.

+ fast unit tests

- an abstraction with one implementation, and the tests skip the real request encoding

Risks

Inherited statuses. The docs list statuses and override_statuses on Get List. I expect the effective set for inheriting lists, but this is not confirmed until verification step 3. If it is wrong, the fallback is the folder's statuses, then the space's.
orderindex type. The model assumes a number, which works for tasks today. Verify that list responses use a number too.
Custom ID detection still uses the existing hyphen check, with the same limits as tasks <id>.
Statuses change between GET and PUT: the API rejects the PUT and the wrapped error is shown.
Tasks in multiple lists: the status comes from the home list, which is what task.list returns.
Three requests per change. Fine for an interactive command.

Out of scope: status tab-completion, and moving the existing commands to cmd.OutOrStdout().
