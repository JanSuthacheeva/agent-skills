Bounded change clickup-cli Approved

clickup tasks status <id> <status>

Change a task's status in one command. The status is checked against the task's own list. An invalid status changes nothing, exits 1, and lists the valid statuses.

Agreed decisions

Matching

Case-insensitive, otherwise exact (strings.EqualFold). The list's own spelling is sent to the API.

Success output

One line: HGAI-1217: to do -> in progress. With --output json, the updated task is printed instead.

Already in that status

The notice is printed, the PUT is skipped, and the command exits 0. In JSON mode, the notice goes to stderr and the current task JSON goes to stdout.

What it looks like

Valid status (any case)
clickup tasks status HGAI-1217 "In Progress"
HGAI-1217: to do -> in progress
Already there
clickup tasks status HGAI-1217 "in progress"
HGAI-1217 is already "in progress"
Invalid status (stderr, exit 1)
clickup tasks status HGAI-1217 done
Error: invalid status "done" for list "Sprint 12". Valid statuses:
  to do
  in progress
  review
  complete

Statuses appear in orderindex order, which is the order shown on the ClickUp board. The text is returned from RunE, and the existing Execute() adds the Error: prefix and exits 1.

Flow

At most three API calls. The PUT uses the native task ID returned by the first GET, so the custom-ID query parameters are only needed once.

Current state (verified)

  • tasksCmd takes an optional [task_id] with MaximumNArgs(1) (internal/commands/tasks.go:24-39). Cobra resolves subcommands first, so tasks HGAI-1217 is unaffected. The only casualty is a task literally named status.
  • --output is a local flag on tasksCmd (tasks.go:46), so subcommands don't see it.
  • doRequest sends no body. Only Get exists (internal/api/client.go:42-96).
  • The custom-ID query logic is duplicated in GetTask and GetTaskComments.
  • bug [DEBUG] lines go to stdout (client.go:49,72-75), so --debug --output json produces invalid JSON. This plan fixes it while touching doRequest.
  • There are no API-layer tests yet. baseURL is an unexported field, so in-package tests can point it at httptest.

Testing (TDD)

  1. models: "In Progress" matches and returns in progress. "progress" and "" are rejected. Status names come out in orderindex order no matter what order they go in.
  2. api client (httptest): Put sends PUT, a JSON body, and the auth header. Get sends no body. Debug output goes to stderr.
  3. api tasks/lists (httptest): the request path and body of UpdateTaskStatus. GetList decodes statuses. Custom-ID GetTask still sets custom_task_ids and team_id, which guards the refactor.
  4. command (fake statusUpdater): success line, canonical spelling sent, invalid status (no PUT, every status listed in order), no-op in any case (no GetList, no PUT), JSON mode, and API failures wrapped with context.
  5. make check passes.
  6. E2E on a throwaway task in a real workspace: custom ID and native ID, wrong case, invalid status (check echo $? is 1), no-op, --output json, --debug --output json | jq ., and a list that inherits its statuses from the folder or space.

Risks

  • Inherited statuses: GET /list/{id} returns the list's effective statuses. The E2E step checks this against a list that inherits.
  • Tasks in multiple lists: the status belongs to the home list, which is task.List. This is correct.
  • One extra GET per change, skipped on a no-op. This is fine for an interactive CLI.
