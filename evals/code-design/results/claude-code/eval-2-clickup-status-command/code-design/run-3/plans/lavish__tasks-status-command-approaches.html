Code design - phase 2 of 4 - approaches

Where should clickup tasks status <id> <status> live?

The command changes a task's status, validates the target against the statuses of the task's home list, and lists the valid ones when the name is wrong. The decision here is which layer owns the fetch-validate-update flow, and whether validation happens before or after the write.

What exists today

  • Commands own orchestration. getTask fetches the client and config, calls the API, fetches the parent task, and formats output - all in the command layer (internal/commands/tasks.go:100-159). There is no service layer.
  • tasks takes an optional positional ID with cobra.MaximumNArgs(1) (tasks.go:24-39). Adding status as a cobra subcommand of tasksCmd is compatible: cobra matches subcommand names first, and since Args is set, clickup tasks HGAI-1217 keeps working.
  • Commands register in init() via rootCmd.AddCommand (tasks.go:41-50); flags are package-level vars.
  • The API client is read-only. doRequest(method, path, query) always sends a nil body, and only Get exists (internal/api/client.go:42-96). A write needs body support and a Put.
  • API methods live in domain files and return pkg/models types (api/tasks.go:59-83, api/comments.go:13-33). Custom IDs like HGAI-1217 need custom_task_ids + team_id (api/tasks.go:66-70).
  • Status shape already exists: models.Status{ID, Status, Color, Type, Orderindex} (pkg/models/task.go:55-61). Task.List carries only ID, Name, Access (task.go:80-84) - no statuses, so the list must be fetched (GET /list/{id}).
  • Errors are wrapped with fmt.Errorf("failed to ...: %w", err) and printed once as Error: ... by Execute (root.go:48-53); API failures are *api.APIError (api/errors.go:8-23).
  • Tests are plain testing table/subtests on models and formatters (pkg/models/task_test.go, internal/output/table_test.go); no command or HTTP tests yet.
The build is broken on main right now. DetailFormatter.FormatComments is declared twice (internal/output/table.go:191 and :238), so go build ./..., go vet and make test all fail. A. Command orchestrates, validation in the model

recommended

A new tasks_status.go subcommand does what getTask does today: get the task, get its list, check the name, then write. Matching a name against a list's statuses is a pure method on a new models.List, so the one piece of real logic is unit-testable without any fakes. The API layer gains three thin methods.

Touches

  • new internal/commands/tasks_status.go
  • internal/api/client.go - body param, Put
  • new internal/api/lists.go; api/tasks.go - UpdateTaskStatus
  • new pkg/models/list.go (+ test)
  • tasks.go / root.go help text, README.md, skills/SKILL.md

Fit with conventions

Mirrors getTask exactly: orchestration in the command, one API method per endpoint in a domain file (api/comments.go), models own small behaviour (Task.GetDisplayID, task.go:36).

Gains
  • Smallest change; reads like the sibling command.
  • Validation logic is pure and trivially testable.
  • Valid statuses come from the same source the write uses, so the error message is always accurate.
Costs
  • 3 HTTP calls on the happy path (task, list, update).
  • Command orchestration stays untested - same gap as getTask today.
  • If more write commands follow (assign, priority, due), each re-does the fetch-check-write dance in its command.

B. New service layer behind an interface

Introduce internal/service with a TaskService.ChangeStatus(taskID, status) that owns the whole flow and returns a typed *InvalidStatusError{Valid []models.Status}. It depends on a small TaskAPI interface that *api.Client satisfies, so the flow can be tested with a fake. The command only parses args and prints.

Touches

  • everything in A, plus
  • new internal/service/tasks.go, errors.go, tests with a fake TaskAPI
  • root.go - a getTaskService() beside getAPIClient()

Fit with conventions

Matches your layering principle (thin entry point, logic in a service), but no such layer exists here: every other command calls *api.Client directly (tasks.go:63-83, config_cmd.go, install.go). One command would follow a different pattern until the others are migrated.

Gains
  • The whole flow, including "already in that status" and error mapping, is unit-tested with a fake.
  • A home for the next write commands.
Costs
  • New package, interface and wiring for one ~40-line flow.
  • Two patterns side by side until listTasks/getTask are moved over - a migration nobody asked for yet.
  • Interface defined for testability only; with a single implementation it is indirection.

C. Write first, explain on failure

Send PUT /task/{id} straight away and let ClickUp validate. Only if it rejects the status, fetch the task and its list and print the valid statuses. Same units as A, different order.

Gains
  • 1 HTTP call on the happy path.
  • ClickUp is the source of truth; no client-side matching rules.
Costs
  • Has to recognise "invalid status" from ClickUp's error body (err/ECODE, api/errors.go:11-12) - an undocumented contract that can drift.
  • Does not really "validate against the list" as asked; it diagnoses after the fact.
  • No control over matching (case, whitespace) or the "already in that status" case.

Recommendation: A

It is the shape the codebase already has, and it puts the only non-trivial logic (matching a name against list statuses) in a pure, tested model method. The extra two GETs cost a few hundred milliseconds on an interactive command, which buys a reliable error message instead of parsing ClickUp error codes (C).

B is the right structure once there are several write commands - but introducing it for one command splits the codebase into two patterns. If you want B, I would suggest doing it as its own refactor that also moves listTasks and getTask, so there is one pattern again. I'll make the case for that on the implementation page if you pick it.
