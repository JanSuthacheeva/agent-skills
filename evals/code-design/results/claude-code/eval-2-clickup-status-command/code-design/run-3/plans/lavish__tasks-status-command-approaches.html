Code design - phase 2 of 4 - pick an approach

Where does clickup tasks status <id> <status> live?

The command must fetch the task, fetch its list's statuses, validate the requested status, and only then update the task - printing the valid statuses when the input is wrong. The decision is which layer owns that orchestration and validation.

new modified existing

What exists today

  • Commands orchestrate. getTask calls the client several times (task, parent, comments), wraps errors as fmt.Errorf("failed to ...: %w"), warns on stderr, and picks a formatter. There is no service layer. internal/commands/tasks.go:100-159
  • One command, positional ID. tasks [task_id] with MaximumNArgs(1), aliases task, t; flags are local, not persistent. internal/commands/tasks.go:24-50 Cobra resolves a subcommand status before falling back to the positional ID, so tasks status ... can coexist with tasks HGAI-1217.
  • The API client is read-only. doRequest sends no body and only Get exists; errors become *APIError. internal/api/client.go:42-96 internal/api/errors.go:8
  • Custom IDs (HGAI-1217) need custom_task_ids=true&team_id= on every task endpoint. internal/api/tasks.go:59-95
  • Models: Task.List only carries ID/Name/Access - no statuses; models.Status already matches the list-status JSON shape and is reusable. pkg/models/task.go:26, 55-61
  • Errors reach the user as Error: %v on stderr with exit 1. internal/commands/root.go:48-53
  • Tests exist for models and output only; nothing tests commands or the client. pkg/models/task_test.go internal/output/table_test.go
main does not build. DetailFormatter.FormatComments is declared twice (a bad merge in 7411557): internal/output/table.go:191 (with word wrap) and :238 (without). Any approach starts by deleting the second copy, as its own commit.

A - Command orchestrates, validation lives on the model

Recommended

A new tasksStatusCmd subcommand in its own file follows the getTask shape: get task, get list, match, update, print. The match itself is a pure method on a new models.List (find a status case-insensitively), so the one piece of real logic is unit-testable without HTTP. The client gains GetList, UpdateTaskStatus and body support.

Touches

  • commands/tasks_status.go (new)
  • commands/tasks.go (register, help text)
  • api/client.go (body, Put)
  • api/tasks.go, new api/lists.go
  • new pkg/models/list.go
  • README, skills/SKILL.md

Fits / gains

  • Same shape as getTask tasks.go:100
  • Same API file-per-domain pattern api/comments.go
  • Model helper like GetDisplayID task.go:36
  • Validation testable as a pure function

Costs

  • Orchestration (3 calls, ordering, error mapping) has no test seam - api.Client is concrete and baseURL is unexported
  • 3 HTTP calls per change (GET task, GET list, PUT)
  • Command file holds flow logic; if more write commands come, this repeats

B - New service package owns the change

Introduce internal/tasks with a StatusChanger that depends on a small interface (GetTask, GetList, UpdateTaskStatus) satisfied by *api.Client. It runs the whole flow and returns a typed *InvalidStatusError carrying the valid statuses. The command becomes a thin adapter: parse args, call, format.

Touches

  • Everything in A, plus
  • new internal/tasks/status.go + test with a fake client

Fits / gains

  • Whole flow unit-testable (wrong status never PUTs, canonical name sent, etc.)
  • Clear controller / service split
  • Precedent for future write commands (assign, comment)

Costs

  • New layer the codebase has nowhere else; getTask stays command-orchestrated, so two styles coexist
  • Interface defined for one consumer
  • More files for ~60 lines of logic

C - Update optimistically, explain on rejection

Not recommended

PUT the status straight away and let ClickUp validate. Only when the API rejects it, fetch the task and its list to print the valid statuses. One call on the happy path instead of three.

Touches

  • Same files as A

Gains

  • 1 HTTP call when the status is right
  • ClickUp is the single source of truth

Costs

  • Depends on ClickUp's error code for "unknown status", which I have not verified and which APIError only exposes as a string errors.go:12
  • Can't tell a bad status from other 400s reliably
  • No canonical-name normalisation (case) before sending

Recommendation: A

A is the shape the codebase already uses - commands orchestrate, the client is a thin HTTP mapper, models carry small helpers - and it isolates the one real rule (does this status exist on the list, case-insensitively) in a pure, tested function. B is the better structure if this is the first of several write commands (assign, comment, move); for a single command it adds a layer the rest of the code does not have. C trades robustness for one saved round-trip on an interactive CLI, which is the wrong trade.

Shared by every option: fix the duplicate FormatComments first; add request bodies to doRequest; the subcommand is tasks status under tasksCmd, so t status works too.
