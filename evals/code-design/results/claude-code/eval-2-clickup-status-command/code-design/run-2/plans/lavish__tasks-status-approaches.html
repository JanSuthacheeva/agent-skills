Code design - phase 2 of 4

Where does status validation live?

Feature: clickup tasks status <id> <status> changes a task's status, validates it against the statuses of the task's list, and lists the valid ones when the given status is wrong. Pick one of three structures below.

new modified existing - - -> error path only

What exists today

  • tasks is a single Cobra command, Args: cobra.MaximumNArgs(1); one arg means "show task" (internal/commands/tasks.go:24-39, :52-60). No subcommands exist anywhere yet. Adding status as a child of tasksCmd works: Cobra matches subcommands before positional args, and the explicit Args validator keeps clickup tasks HGAI-1217 working.
  • Command funcs own the orchestration: fetch config + client via getAPIClient()/getConfig() (root.go:79-105), call several API methods, wrap errors with fmt.Errorf("failed to ...: %w") (tasks.go:111-124 fetches the task, then its parent). Errors bubble to Execute(), printed as Error: ... (root.go:48-53).
  • The API layer is thin: one Client method per endpoint, one file per domain (api/tasks.go, api/comments.go, api/user.go), custom-ID handling via isCustomTaskID (api/tasks.go:66-70).
  • The HTTP client only does GET with no request body: doRequest(method, path, query) passes nil body (api/client.go:42-52), and only Get is exposed (:94). Any write needs a body-capable doRequest and a Put.
  • models.Status already exists (pkg/models/task.go:55-61); models.ListInfo only has id/name/access (:80-84), so list statuses need a new models.List from GET /list/{id}.
  • API errors are a single *APIError with status code and ClickUp's err/ECODE (api/errors.go:8-23); nothing type-switches on errors yet.
Pre-existing build break: DetailFormatter.FormatComments is declared twice (internal/output/table.go:191 and :238), so go build ./... and make check fail on main today. Whichever approach you pick, the plan starts by deleting the older, non-wrapping copy at :237-279.

A. Validate up front in the command

recommended

The command fetches the task, then its list, and checks the requested status against the list's statuses (case-insensitive, via a small models.List.FindStatus helper) before writing. The API layer just gains two thin endpoint methods. Same shape as getTask fetching task + parent today.

Touches

new commands/tasks_status.go, new api/lists.go, new models/list.go, api/tasks.go (+UpdateTaskStatus), api/client.go (body + Put), README + skills/SKILL.md.

Fit

Orchestration in the command like getTask (tasks.go:100-124); one method per endpoint in api (api/comments.go:13); errors as wrapped fmt.Errorf.

Benefits

  • Exact, friendly error with the full list before anything is written.
  • Case-insensitive input; sends the canonical name.
  • Can short-circuit "already in that status".
  • FindStatus is a pure function: trivial unit test.

Costs

  • 3 HTTP calls per change (task, list, update) - ~300-600ms extra vs one call.
  • Small race: list statuses could change between check and write (API still rejects then).

B. Write optimistically, explain on failure

The command sends the PUT straight away and lets ClickUp validate. Only if ClickUp rejects it as an unknown status does the command fetch the task and its list to print the valid statuses. Needs a way to recognise "invalid status" in *APIError.

Touches

Same files as A, plus api/errors.go (+IsInvalidStatus); no models.List.FindStatus.

Fit

Command orchestration fits; but it introduces the first error classification in the codebase, keyed on an undocumented ClickUp ECODE/message.

Benefits

  • 1 HTTP call on the happy path - fastest.
  • No check/write race: ClickUp is the single source of truth.

Costs

  • Depends on ClickUp's undocumented error code for "status not found"; silently degrades to a raw API error if it changes.
  • Case handling is whatever ClickUp does; we cannot normalise input without the list.
  • No "already in status" detection without an extra fetch.
  • Harder to test: requires faking specific HTTP error bodies.

C. A validating operation in the API layer

Same three calls as A, but bundled into one Client.SetTaskStatus that returns a typed *InvalidStatusError{Requested, List, Valid}. The command becomes a thin wrapper that type-checks the error to render the valid statuses.

Touches

Same as A, plus a typed error in api/errors.go.

Fit

Deviates: today every Client method is one endpoint (api/tasks.go:22,59, api/comments.go:13) and multi-call orchestration lives in commands (tasks.go:111-124).

Benefits

  • Reusable if a future command (bulk move, TUI) needs the same validated change.
  • Typed error is cleaner than string-built messages.

Costs

  • Turns the HTTP client into a service layer; mixes transport and business rules.
  • Testing the rule needs an HTTP fake instead of a pure function.
  • Speculative reuse - there is no second caller today.

Recommendation: A

A is the only option that gives the exact behaviour you asked for ("validate against the list, show the valid ones") deterministically, without betting on an undocumented ClickUp error code (B) or bending the thin API client into a service (C). The cost is two extra GETs per status change, which is noise for an interactive CLI. The matching rule lives in a pure models helper, so it is unit-testable without HTTP. If a second caller ever appears, A's command logic can be extracted into C later without changing any API method.
