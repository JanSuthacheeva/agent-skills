Where should status validation live for clickup tasks status <id> <status>?

Pick one structure. Signatures, data shapes and call chains come on the implementation page once this is settled.

What exists today

  • tasksCmd is tasks [task_id] with MaximumNArgs(1); no subcommands yet (internal/commands/tasks.go:24-39). Its local --status flag is a list filter, not inherited by subcommands (tasks.go:44).
  • Commands orchestrate: getTask fetches the task, then optionally the parent task, then formats (tasks.go:100-159). Errors are wrapped with fmt.Errorf("failed to ...: %w") and printed once by Execute as Error: ... (root.go:48-53).
  • API methods are thin endpoint wrappers on *api.Client, one domain per file (api/tasks.go, api/comments.go, api/user.go), each handling custom IDs via isCustomTaskID + team_id (api/tasks.go:66-70).
  • The HTTP layer is GET-only: doRequest(method, path, query) never sends a body, and only Get is exported (api/client.go:42-96). A PUT with a JSON body is new plumbing either way.
  • models.Status exists (pkg/models/task.go:55-61); models.ListInfo holds only id/name/access (task.go:80-84). No list model with statuses, no list endpoint.
  • Non-API errors are plain fmt.Errorf; the only typed error is *api.APIError (api/errors.go:8-23).
  • Tests: models and output only (pkg/models/task_test.go, internal/output/table_test.go). None for api or commands.
main does not build right now. DetailFormatter.FormatComments is declared twice (internal/output/table.go:191 and :238, the second an older non-wrapping copy left by the last merge). make check fails. Every approach below starts by deleting the stale copy at :238.

ClickUp endpoints involved: GET /task/{id} (gives list.id), GET /list/{list_id} (returns the list's effective statuses), PUT /task/{id} with {"status": "..."}. The API itself also rejects unknown statuses with a 400.

A. Command orchestrates, validate up front

recommended

The status subcommand does what getTask already does: call thin API methods in sequence - get task, get its list, match the requested status, update. The matching rule ("case-insensitive name match, return the canonical status") is a small pure method on a new models.List, so it is unit-testable without HTTP.

Touches

  • new commands/tasks_status.go (subcommand of tasksCmd)
  • new api/lists.go; api/tasks.go + UpdateTaskStatus; api/client.go body support + Put
  • new pkg/models/list.go
  • docs: README.md, skills/SKILL.md, root help

Fit

Same shape as getTask chaining GetTask calls (tasks.go:111-124); API stays one-endpoint-per-method (api/tasks.go:59); helpers on models like GetDisplayID (task.go:36).

Benefits

  • Valid statuses are known before any write; error message is fully ours.
  • Typo-tolerant: "In Progress" matches "in progress" and we send the canonical name.
  • Can detect "already in that status" and skip the PUT.
  • GetList is reusable (e.g. a future clickup lists or shell completion of statuses).

Costs

  • 3 requests on the happy path (task, list, update) - roughly 3x latency of a bare PUT.
  • Small race: status set could change between GET list and PUT (API still rejects, we surface its error).

B. Try the update, explain only on rejection

The command sends the PUT straight away. If ClickUp rejects it as an unknown status, it then fetches the task and its list to print the valid statuses. Validation is effectively delegated to the API; we only decorate its error.

Touches

  • same files as A, plus api/errors.go (ECODE classification)
  • no models.List matching logic needed

Fit

Uses the existing APIError.ECODE field (errors.go:12), which nothing branches on today. Requires error-driven control flow in a command, which the codebase does not do anywhere.

Benefits

  • 1 request on the happy path - fastest.
  • No race: the API is the single source of truth.

Costs

  • Depends on an undocumented, unversioned ECODE string to recognise "invalid status" - silent breakage if ClickUp changes it.
  • Case/whitespace typos depend on API leniency; we cannot normalise to the canonical name.
  • No "already in that status" detection without an extra GET anyway.
  • Harder to test: the interesting path is the failure path.

C. API client owns the use case

Same pre-validation as A, but packaged as one high-level method Client.SetTaskStatus(taskID, teamID, status) that internally does the three calls and returns a typed *api.InvalidStatusError{Valid []models.Status}. The command becomes a thin shell that formats the result.

Touches

  • same files as A, plus api/errors.go (new error type)

Fit

Deviates: every existing Client method maps to exactly one endpoint (api/tasks.go:22,59, api/comments.go:13), and multi-call orchestration lives in commands (tasks.go:111-124).

Benefits

  • Use case reusable from any future caller (e.g. a bulk command).
  • Typed error lets the command render valid statuses however it likes.

Costs

  • Mixes business rules into the transport package; it stops being a plain client.
  • Testing the rule requires an HTTP fake rather than a pure function.
  • Speculative reuse - there is no second caller today.

Recommendation: A

A follows the existing split exactly (commands orchestrate, the client wraps endpoints, models hold small pure helpers), gives the most robust validation and the best error message, and keeps the matching rule unit-testable. B's speed win is two GETs on a command a human runs by hand, and it buys that with a dependency on an undocumented error code. C is A with the orchestration moved into the wrong layer.

Smaller choices (output format on success, same-status no-op, how the valid list is printed, whether -o json is supported) are settled on the next page as assumptions you can overturn.
