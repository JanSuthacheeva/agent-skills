clickup tasks status <id> <status>

new modified existing

1. Decision recap

A new status subcommand of tasks orchestrates thin API calls the same way getTask does: get the task, get its list, match the requested status with a pure helper on a new models.List, then update. Nothing is written if the status does not exist in the list; the valid statuses are shown instead.

  • Decided in phase 2: approach A, because it matches the existing getTask pattern.
  • Decided in phase 2: step 0 deletes the stale duplicate DetailFormatter.FormatComments (internal/output/table.go:237-281) so the build is green before any feature work.

2. Structure overview

The command depends on the client (task + list endpoints), on models.List for matching, and on root.go for the shared client/config. models.List reuses the existing models.Status. table.go is unrelated to the feature; it is only touched to unbreak the build.

5. Call chains

5a. clickup tasks status HGAI-1217 In Progress - valid status

  1. cobra -> runTasksStatus(cmd, ["HGAI-1217", "In", "Progress"]): error
  2. runTasksStatus -> setTaskStatus(cmd.OutOrStdout(), "HGAI-1217", "In Progress"): error
  3. setTaskStatus -> getAPIClient(): (*api.Client, error)
  4. setTaskStatus -> getConfig(): (*config.Config, error)
  5. setTaskStatus -> Client::GetTask("HGAI-1217", cfg.WorkspaceID): (*models.Task, error) - GET /task/HGAI-1217?custom_task_ids=true&team_id=...
  6. setTaskStatus -> Client::GetList(task.List.ID): (*models.List, error) - GET /list/{list_id}
  7. setTaskStatus -> List::FindStatus("In Progress"): (models.Status, bool) - returns {Status: "in progress"}, true
  8. If strings.EqualFold(task.Status.Status, match.Status): fmt.Fprintf(w, ...) prints HGAI-1217 is already "in progress", return nil (no PUT).
  9. setTaskStatus -> Client::UpdateTask("HGAI-1217", cfg.WorkspaceID, &api.UpdateTaskRequest{Status: "in progress"}): (*models.Task, error)
    1. UpdateTask -> taskIDQuery("HGAI-1217", teamID): url.Values
    2. UpdateTask -> Client::Put("/task/HGAI-1217", query, req): ([]byte, error) -> doRequest(http.MethodPut, path, query, req) - body {"status":"in progress"}
    3. Decode body into models.Task.
  10. setTaskStatus -> fmt.Fprintf(w, "%s: %s -> %s\n", updated.GetDisplayID(), task.Status.Status, updated.Status.Status) prints HGAI-1217: to do -> in progress; return nil, exit 0.

Error paths (all returned up to Execute, printed to stderr as Error: ..., exit 1, nothing written)

  • Fewer than 2 args: cobra MinimumNArgs(2) -> Error: requires at least 2 arg(s), only received 1 (usage silenced by rootCmd.SilenceUsage).
  • Step 3/4: missing or unreadable config -> error from config.Manager.Load, returned unwrapped (same as getTask).
  • Step 5: unknown ID, no access, network -> failed to get task: API error (status 401): ...
  • Step 6: list not accessible -> failed to get list: API error (status ...): ...
  • Step 7 no match -> chain 5b.
  • Step 9: ClickUp rejects (e.g. statuses changed since step 6) -> failed to update task status: API error (status 400): ...

5b. clickup tasks status HGAI-1217 inprogress - status not in the list

  1. Steps 1-6 as in 5a.
  2. setTaskStatus -> List::FindStatus("inprogress"): (models.Status, bool) - returns Status{}, false.
  3. setTaskStatus -> invalidStatusError("inprogress", list): error -> List::StatusNames(): []string; setTaskStatus returns it. No UpdateTask call.
  4. Execute prints to stderr and exits 1:
clickup tasks status HGAI-1217 inprogress
Error: invalid status "inprogress" for list "Sprint 12". Valid statuses:
  to do
  in progress
  review
  complete

If the list reports no statuses at all, invalidStatusError returns list "Sprint 12" has no statuses instead of an empty list.

Deviations

  • setTaskStatus takes an io.Writer where getTask writes to os.Stdout directly (tasks.go:142), so its output can be asserted in tests. Same spirit as the formatters, which all take w io.Writer.
  • First nested subcommand in the codebase (tasksCmd.AddCommand instead of rootCmd.AddCommand). Cobra still routes clickup tasks HGAI-1217 to tasksCmd because it has explicit Args; custom IDs always contain -, so none can collide with status.
  • Named UpdateTaskRequest rather than ...Options: it is a JSON body, not query options.

8. Assumptions

  1. Status matching ignores case and surrounding whitespace; the list's exact spelling is what gets sent.
  2. Multi-word statuses work with or without quotes: everything after the ID is joined with single spaces.
  3. If the task already has that status: prints HGAI-1217 is already "in progress", exit 0, no write.
  4. Success prints one line to stdout: HGAI-1217: to do -> in progress. No -o/--output on this subcommand.
  5. Invalid status: nothing is written; stderr lists every valid status in board order, one per line; exit 1.
  6. No "did you mean" fuzzy suggestion; the full list is short enough.
  7. Closed/done-type statuses are allowed like any other.
  8. Valid statuses come from GET /list/{id}, assumed to return the list's effective statuses even when inherited from folder/space. Checked first in E2E with --debug before building on it.
  9. A list reporting no statuses is an error, never "skip validation".
  10. Native and custom IDs both work; the global --workspace override is honoured via getConfig.
  11. If statuses change between the check and the update, ClickUp's rejection is shown as failed to update task status: ...; no retry.
  12. Docs updated (README, skills/SKILL.md, root and tasks help) and bin/ binaries rebuilt with make build-all.
