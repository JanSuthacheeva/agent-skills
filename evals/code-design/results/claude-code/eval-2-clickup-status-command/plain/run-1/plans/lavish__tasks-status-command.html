Plan clickup-cli first write operation

clickup tasks status <id> <status>

Change a task's status from the CLI. The status is validated against the statuses of the task's own list. If it is invalid, nothing is written and the valid statuses are printed in workflow order.

Target behavior

Valid change
$ clickup tasks status HGAI-1217 review HGAI-1217: in progress -> review $ clickup tasks status HGAI-1217 In Progress HGAI-1217: review -> in progress # case-insensitive, unquoted multi-word joined
Invalid status (exit 1, nothing written)
$ clickup tasks status HGAI-1217 done Error: invalid status "done" for list "Sprint 12" Valid statuses: to do in progress review complete
Already in that status (exit 0, no PUT)
$ clickup tasks status HGAI-1217 review HGAI-1217 is already in "review"

How a call flows

It reads twice and writes at most once. Validation runs before any write, so an invalid status never reaches ClickUp.

  • GET /list/{id} returns the list's effective statuses, including ones inherited from the folder or space.
  • The PUT uses the native task.ID from step 1, so the write path never needs custom_task_ids handling.
  • The PUT sends the canonical name from the list, not the raw user input.

Changes by layer

The command layer only orchestrates. Matching rules live in models as pure functions, and HTTP details stay in the api package.

Verified against the code

Cobra routing is safe

I built a scratch binary on cobra v1.10.2 with the same shape: tasks using MaximumNArgs(1) and a local --status flag, plus a status subcommand.

tasks HGAI-1 -> tasks [HGAI-1] tasks --status "x" -> tasks [] tasks HGAI-1 --status x -> tasks [HGAI-1] tasks status HGAI-1 in progress -> status [HGAI-1 in progress] tasks stauts -> tasks [stauts] # 404, same as today

What exists today

  • doRequest sends no body. Only Get exists, so this is the CLI's first write.
  • GetTask already returns Status and List{ID, Name} and handles custom IDs.
  • models.Status already has Orderindex and Type.
  • There are no API tests yet. This change adds the first httptest coverage.

E2E with the built binary on a throwaway task:

  • Valid change using a custom ID and a native ID. Confirm it in the ClickUp UI.
  • Mixed-case input and unquoted multi-word input.
  • Invalid status: the list is shown, exit code is 1, and the task is unchanged in the UI.
  • Already in status: --debug shows no PUT.
  • A task in a list that inherits space statuses. An unknown task ID.

Risks and edge cases

Tasks in multiple lists - task.list is the home list, and its statuses control the task's status. Correct as is.
Race - if list statuses change between GET and PUT, ClickUp rejects the PUT and the API error is shown. Acceptable.
Shadowing - a task whose ID is literally status would hit the subcommand. Not realistic.
Signature change - doRequest gains a body param. All current callers go through Get, so the change is contained.

Decisions

Unquoted multi-word status

Approved Join args[1:]

tasks status X in progress works without quotes. Quoted input still works.

Success output

Approved One-line confirmation only

Prints <id>: <old> -> <new>. The command gets no -o flag.
