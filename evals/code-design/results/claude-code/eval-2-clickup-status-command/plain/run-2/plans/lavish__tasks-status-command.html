Implementation plan - clickup-cli

Add clickup tasks status <id> <status>

Change a task's status from the CLI. The status is checked against the statuses of the task's own list. If it doesn't match, the command fails and prints the valid statuses. No task is changed until the status is known to be valid.

Valid status
$ clickup tasks status HGAI-1217 "in progress" HGAI-1217: to do -> in progress $ clickup tasks status HGAI-1217 In Progress HGAI-1217 is already "in progress"
Invalid status (exit 1, no write)
$ clickup tasks status HGAI-1217 done Error: invalid status "done" for list "Sprint 12". Valid statuses: to do in progress review complete

Current state (verified in code)

  • tasksCmd (internal/commands/tasks.go:24) takes an optional [task_id] with MaximumNArgs(1) and has no subcommands yet.
  • The API client is read-only. doRequest (internal/api/client.go:42) always sends a nil body, and only Get exists.
  • GetTask (internal/api/tasks.go:59) already resolves custom IDs like HGAI-1217. The returned task has the native ID, Status and List.ID.
  • models.Status exists (pkg/models/task.go:55). There is no List model or list endpoint.
  • No internal/api tests exist yet. Client.baseURL is a field, so in-package tests can point it at httptest.Server.

Flow

  • 1
    GET /task/{id} (existing GetTask): resolves the custom or native ID and gives the current status and list.id.
  • 2
    GET /list/{list_id} (new GetList): returns the list's effective statuses, inherited from the folder or space when the list doesn't override them.
  • 3
    list.FindStatus(input): case-insensitive, trimmed exact match.
    no match error listing valid statuses by orderindex, exit 1
    same as current print "already", exit 0, no write
  • 4
    PUT /task/{native_id} with {"status": canonical}. Because we use the native ID from step 1, no custom-ID query params are needed.
  • 5
    Print HGAI-1217: to do -> in progress

Design decisions

DecisionChoiceWhy
Command shapestatus as a Cobra subcommand of tasksMatches the requested syntax. Cobra resolves subcommands before positional args, so clickup tasks HGAI-1217 still works. The t/task aliases also work.
Validation sourceGET /list/{id} statusesThe list is the authority on statuses. The API also rejects bad statuses, but its error doesn't list the valid ones.
MatchingCase-insensitive exact, send the canonical nameIn Progress should work. No fuzzy/prefix matching - it's too risky for a write.
Write payloadGeneric UpdateTask(id, models.TaskUpdate)Matches the API resource. Adding assignee or priority later means adding a field, not a new method.
Request bodiesdoRequest(..., payload any) plus PutA single place for auth, debug and error mapping. Get passes nil.
Status lookup(*models.List).FindStatusA pure function that is easy to unit test and sits next to the data.
Command fileNew internal/commands/tasks_status.goFollows the register-in-init() convention without making tasks.go bigger.
OutputOne confirmation line, no --outputIt's a mutation, so a short receipt is enough. tasks <id> -o json already exists for reading.

E2E (real binary, throwaway task from Jan)

  1. Custom ID + "in progress" changes the status. Confirm with tasks <id> and in the ClickUp UI.
  2. Native ID works.
  3. In Progress matches and the canonical name is sent.
  4. Unquoted in progress matches.
  5. Invalid status lists statuses in board order, exits 1, and leaves the task unchanged.
  6. Repeating the current status prints "already" with no PUT (check with --debug).
  7. A subtask in a list with custom statuses, and a list that inherits statuses, both validate correctly.
  8. clickup tasks and clickup tasks <id> behave exactly as before.

Risks

Inherited statuses. GET /list/{id} should return the effective statuses even when the list doesn't override them. E2E check 7 covers this. If the list comes back empty, fall back to the statuses from GET /space/{task.space.id}.
A task literally named status would be routed to the subcommand. ClickUp IDs never look like that, so this is acceptable.
--debug prints to stdout (existing behavior) and won't show the request body. This is unchanged and out of scope.

Resolved decisions approved

  1. Unquoted multi-word statuses: join args[1:] (cobra.MinimumNArgs(2)), so clickup tasks status X in progress works.
