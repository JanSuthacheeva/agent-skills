Bookmarks in mdterm - which structure?

ma sets mark a at the current position, 'a jumps back, marks persist per file across sessions. The real decision is what a "position" is once it has to survive a restart, a different terminal width and edits to the file. Everything else is shared by all three approaches.

What exists today

Position = wrapped-line index

The viewport position is ViewerState.offset, an index into wrapped - lines after word-wrapping to the current width and after image rows are expanded.

  • Resize triggers rebuild(), which keeps the same index, so the visible content shifts. viewer.rs:1252, 491-598
  • Image loads re-expand rows and patch offset by a delta. viewer.rs:611-657
  • nav_history: Vec<(usize, usize)> already stores (file, offset) for Backspace. viewer.rs:365, 1765

No source mapping on lines

Line is just spans + meta. The renderer receives source byte ranges per event, but only task checkboxes keep one (bracket_offset).

  • Line / LineMeta style.rs:26-59
  • into_offset_iter() feeds process(event, range) markdown.rs:1585, 705
  • bracket_offset precedent markdown.rs:1108-1113

Keys are single-stroke

handle_event routes by ViewMode to handle_normal, a flat match code. No prefix/chord state exists yet.

  • ViewMode enum viewer.rs:230, dispatch viewer.rs:1062
  • handle_normal viewer.rs:1606; slide mode and JSON nav intercept first viewer.rs:1610-1617
  • Help table is data-driven and tested for duplicate keys viewer.rs:3597, 3976

Persistence precedent

config.rs is the only on-disk state: a small module, dirs::config_dir(), serde + TOML, silent fallback to defaults on any error.

  • Config::load, config_path config.rs:29-43
  • One file per concern in src/ (export.rs, json.rs, ...) CLAUDE.md
  • Errors surface as toasts, never panics viewer.rs:454, 895
Key conflict: m is already "Toggle mouse capture" (viewer.rs:1647, help at viewer.rs:3637). ' and M are unbound. I propose moving mouse capture to M - see the form at the bottom.

Shared by every approach

New module src/marks.rs

A MarkStore that loads and saves marks keyed by canonical file path, mirroring config.rs. Marks are app state, not settings, so they go to dirs::data_dir()/mdterm/marks.json, not into config.toml. Written on every set (read-merge-write, atomic rename) so two open mdterm instances don't clobber each other.

Pending-prefix field, not a new ViewMode

ViewerState.pending_mark: Option<MarkPrefix> consumed at the top of handle_normal. ViewMode means "an overlay is open"; a one-keystroke prefix is not an overlay. Jumping pushes the current spot onto nav_history, so Backspace undoes a jump for free.

Approaches - how a mark remembers its position

A. Store the wrapped offset

not recommended

A mark is the raw offset value. Setting copies state.offset into the store; jumping writes it back and clamps to max_offset(). No change to rendering at all.

Benefits
  • Smallest change: viewer.rs + marks.rs only.
  • Matches nav_history, which already stores raw offsets viewer.rs:1766.
  • Works identically for markdown and JSON views.
Costs
  • Wrong after any width change - and across sessions the width is usually different (other window, split, -w).
  • Wrong as soon as images load at a different height, or line numbers / theme reflow differently.
  • Any edit above the mark shifts it silently.
  • Fails the "persist between sessions" requirement in practice, so it's here as a baseline.

Touches: src/marks.rs (new), src/viewer.rs, src/main.rs (mod marks).

B. Anchor to the source line

recommended

Every rendered Line carries the source line it came from. A mark stores the source line of the top visible line; jumping resolves it to the first wrapped line at or after that source line. Positions are independent of width, theme, line numbers and image loading - the same model bracket_offset already uses.

Benefits
  • Survives resize, other terminal widths, -w, theme and line-number toggles, image loads.
  • Edits below the mark never move it; edits above shift it only by the lines added/removed - the same behaviour as vim marks.
  • Persisted value is human-meaningful ("line 142"), so the file is debuggable.
  • Unlocks fixing the existing resize drift (keep the same source line across rebuild()) with the same field.
Costs
  • Touches the data model: one new field on Line, so ~49 struct literals across 4 files need updating (mechanical: markdown 15, style 11, json 20, viewer 3).
  • wrap_lines and image row expansion in finalize_layout must carry the field.
  • JSON view has no meaningful source lines once nodes collapse; marks there would need a fallback or be markdown-only.
  • Precision is one source line: a long paragraph is one source line, so a mark lands on the paragraph start.

Touches: src/marks.rs (new), src/style.rs, src/markdown.rs, src/viewer.rs, src/json.rs (literals), src/main.rs.

C. Anchor to the nearest heading

viable

A mark stores the heading the viewport is in (text + occurrence index) plus how many wrapped lines below it the top line was. Jumping finds that heading in the existing toc_entries and adds the delta. Documents without headings fall back to a 0..1 fraction of the document.

Benefits
  • No rendering or data-model change; reuses toc_entries viewer.rs:661-697 and toc_entry_for_line viewer.rs:847.
  • Robust to edits in other sections, even large ones above the mark.
Costs
  • The delta is still wrapped lines, so it drifts with width inside long sections.
  • Renaming the heading orphans the mark; duplicate headings need occurrence counting.
  • Two resolution strategies (heading / fraction) to explain and test.
  • Fuzzier mental model: "roughly 12 lines into Installation".

Touches: src/marks.rs (new), src/viewer.rs, src/main.rs.

Recommendation: B

The feature's defining requirement is persistence, and across sessions the one thing that reliably changes is the terminal width - which makes A wrong in the common case and C imprecise. B is the only option where a mark means the same thing every time, and it does it by extending a model the codebase already trusts (bracket_offset keeps a source position through rendering for task toggling). The 49 literal updates are mechanical; the lasting cost is one field on Line. For JSON files I'd keep marks markdown-only in v1 and toast "Marks are not available in JSON view" - decided on the implementation page.
