Bookmarks - implementation design

Approach B: marks anchor to the markdown source line. Signatures only, no bodies. Every name is a proposal, so annotate anything that reads wrong.

1Decision recap

Every rendered Line carries the 0-based source line it came from. A mark saves the source line of the top visible row, and a jump scrolls to the first row rendered from that line or later. Marks persist per file in marks.json under the platform data dir, handled by a new src/marks.rs.

Decided in phase 2
  • Approach B (source line), not raw offset or heading anchor.
  • Mouse capture toggle moves from m to M.
  • Shared: a MarkStore module, a pending-prefix field rather than a new ViewMode, and jumps that push onto nav_history.
Decided in review
  • Marks are a-z only, per file. A-Z cancel like any other key.
  • Resize drift is fixed with the same anchor, as its own commit.
  • JSON view: no marks, shown with a toast.

Deviations

  • data_dir, not config_dir. Marks are app state, not settings, and shouldn't sit next to a hand-edited config.toml.
  • JSON, not TOML. The file is written by the program and never meant to be edited by hand, map keys are arbitrary paths, and serde_json is already a dependency.
  • Atomic temp + rename write. toggle_task uses plain fs::write viewer.rs:891, but marks.json is shared by every document and every running instance, so a torn write would lose all marks.
  • First chord state. No key prefix exists today. It's a ViewerState field rather than a ViewMode, because modes represent overlays viewer.rs:230.

8Assumptions

  • Mark names are a-z only, local to the file (26 per file). A-Z cancel the pending prefix like any other non-a-z key.
  • Setting an existing mark overwrites it without asking.
  • A mark saves the top visible row's source line. If that row continues a wrapped paragraph, the jump lands on the paragraph's first row, a few rows higher.
  • A jump puts the marked row at the top of the viewport, clamped near the end of the document.
  • If the file shrank below the mark, the jump goes to the end of the document without an error.
  • A jump pushes onto nav_history, so Backspace returns to where you were.
  • After m or ' the next key is always consumed. a-z acts; anything else (A-Z, Esc, digits, h, ?, F1, Tab) cancels silently. Ctrl+c still quits.
  • While waiting for the letter, the status bar shows m█ or '█.
  • Toasts: "Mark a set", "Jumped to mark a", "Mark a not set", "Marks need a file on disk", "Marks are not available in JSON view", "Mark a set, not saved: <error>".
  • Marks do nothing in slide mode, where m and ' stay unbound.
  • JSON view has no marks. A .json file that fails to parse and falls back to markdown rendering does support them.
  • A resize, reload, theme or line-number toggle keeps the same source line at the top of the viewport. JSON view keeps today's offset behaviour.
  • stdin input has no marks, because it has no stable identity.
  • A file is identified by its canonical absolute path: renaming or moving a file loses its marks, and symlinks resolve to their target.
  • Storage is dirs::data_dir()/mdterm/marks.json: ~/Library/Application Support/mdterm/ on macOS, ~/.local/share/mdterm/ on Linux. It is written on every set.
  • With several mdterm instances open, each set re-reads the file and merges into it. The last writer wins per file and letter. Marks set in another instance become visible after your next set or a restart.
  • A corrupt marks.json is ignored on load and never overwritten. Marks keep working for the session, with a toast.
  • No delete, list or overlay for marks in v1. Entries for deleted files are never pruned.
  • Source lines are 0-based in memory and on disk.
  • Precision is per line inside code blocks; tables, mermaid diagrams and images resolve to the block start.
  • Mark keys work while search results are active, and n/N are unaffected.
  • The m to M move for mouse capture is a breaking key change and gets a mention in the commit/PR description.
