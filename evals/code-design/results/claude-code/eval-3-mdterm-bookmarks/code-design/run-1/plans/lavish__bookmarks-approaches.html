Bookmarks in mdterm - pick an approach

m+letter sets a mark, '+letter jumps to it, marks persist per file across sessions. The decision: what a mark remembers and who owns it.

What exists today

Keys and state

  • All keys go handle_event -> handle_normal as a flat match code (src/viewer.rs:993, :1606). There is no multi-key sequence handling anywhere yet.
  • Every piece of viewer state lives on one ViewerState struct (src/viewer.rs:283); SearchState is the one sub-state with its own type and methods (:2178).
  • Position = state.offset, an index into wrapped lines, i.e. after word-wrap at the current width and after image rows are expanded (:575, :605-657).
  • Closest sibling: nav_history: Vec<(usize, usize)> stores (file_idx, offset) for Backspace (:365, :1765, :1966) - in-memory only.

Persistence and layout

  • The only thing mdterm reads from disk besides documents is config.rs: Config::load() from dirs::config_dir()/mdterm/config.toml, errors silently fall back to defaults (src/config.rs:29-43). Nothing is ever written to app dirs today.
  • Line carries spans + LineMeta only - no link back to the source (src/style.rs:56). The renderer does see byte ranges via into_offset_iter (src/markdown.rs:1585) and already uses them for TaskItem.bracket_offset.
  • Errors in the TUI surface as 1s toasts via set_toast (src/viewer.rs:454), e.g. "Write failed" in toggle_task (:895).
Key conflict: m is already "Toggle mouse capture" (src/viewer.rs:1647, help at :3637). Something has to move - see the second question in the form. (Side note: m is also missing from the README controls table, README.md:94-110 - I would fix that in the same change.)
Why "what a mark remembers" matters: a wrapped-line offset is only meaningful for one terminal width, one line-numbers setting and one set of loaded images. The same file opened tomorrow in a narrower window puts offset 412 somewhere else. Persistence across sessions is exactly where this breaks.

A - Viewer-local, store the wrapped offset

Everything lives in viewer.rs: a pending-prefix field and a HashMap<char, usize> of wrapped offsets on ViewerState, plus a couple of free functions mirroring config.rs that read/write a marks file. A mark is literally the offset value, like nav_history.

Touches: src/viewer.rs only (+ help, README). Fits the "it's all in ViewerState" habit (:283), but grows a 4356-line file further.

Benefits

  • Smallest diff, no new module.
  • Same shape as nav_history.

Costs

  • Wrong after reopen at another width, after toggling line numbers, after resize, and while images load (finalize_layout shifts rows). Breaks the core requirement.
  • Persistence I/O mixed into the TUI file; only testable through ViewerState.

B - marks.rs module, heading-relative anchor

New marks.rs owns the mark type and the per-file store (load, set, save). A mark remembers the nearest heading above (its slug, as navigate_to_anchor already matches at src/viewer.rs:1979) plus how many wrapped lines below it you were. The viewer converts offset <-> anchor using the existing toc_entries; the renderer is untouched.

Touches: new src/marks.rs, src/viewer.rs, src/main.rs (mod marks;). Fits the one-file-per-concern layout listed in CLAUDE.md and the config.rs load pattern.

Benefits

  • No change to rendering or Line.
  • Survives edits above the heading and most width changes.
  • Persistence is isolated and unit-testable.

Costs

  • The delta is still in wrapped lines, so inside a long section it drifts with width - wrong by a screen in long prose.
  • Documents without headings degrade to A. Duplicate heading texts need disambiguation.
  • A heuristic: hard to explain when it misses.

C - marks.rs module, source-line anchor recommended

Same marks.rs as B, but a mark remembers the source line of the markdown block at the top of the viewport. To get it, Line gains a source-position field that the renderer stamps from the byte ranges it already receives and that wrap_lines copies to every wrapped piece. Offset -> mark reads wrapped[offset]; mark -> offset finds the first wrapped line at or after that source line.

Touches: new src/marks.rs; src/style.rs (Line, wrap_lines/word_wrap); src/markdown.rs (~15 Line constructions); src/json.rs (~20 constructions, get "no source position"); src/viewer.rs; src/main.rs. Mirrors how TaskItem.bracket_offset already threads a source byte offset from renderer to viewer (src/style.rs:42, src/markdown.rs:1108).

Benefits

  • Exact across width, resize, theme, line numbers and image loading - the layout never enters the stored value.
  • Human-readable file ("line 142"), drifts like vim marks only when the file is edited above the mark.
  • Source position on Line is reusable later (e.g. "open in $EDITOR at this line", keeping position across live reload).

Costs

  • Largest diff: ~50 Line { .. } sites across three files get a new field.
  • Granularity is one markdown block: inside a long wrapped paragraph or code block the jump lands at the block start (code blocks could be per-line - decided on the next page).
  • Renderer changes need care so every emitted line gets the right position.

Recommendation

C. Persistence across sessions is the point of the feature, and only C stores something the next session can interpret correctly regardless of terminal size. A cannot meet the requirement; B is a heuristic that fails silently in exactly the long documents where bookmarks are most useful. C's cost is a wide but mechanical change to Line, which is development cost - and it follows the existing bracket_offset precedent rather than inventing a new mechanism.

Shared by B and C regardless of choice: marks file in dirs::data_dir()/mdterm/marks.toml (state, not config), keyed by canonical file path, written immediately on each m+letter; stdin documents get in-session marks only. These go on the assumptions list next round.
