mdterm bookmarks - how to structure it

m+letter sets a mark, '+letter jumps back, marks persist per file between sessions. Decision: what a mark is anchored to, and where mark state and persistence live.

What exists today

Keys and modes

  • All keys go through handle_event (src/viewer.rs:993), then per-mode handlers; Normal mode is handle_normal (src/viewer.rs:1606), one flat match code.
  • No key-sequence support yet: every binding is a single key. Multi-key flows today are ViewMode variants (src/viewer.rs:230) - Search, Toc, FuzzyHeading...
  • Slide mode and JSON nav intercept keys before the Normal match (src/viewer.rs:1610-1617).
  • Help overlay entries are a static table (src/viewer.rs:3597), guarded by a no-duplicate-keys test (src/viewer.rs:3976).

Position and navigation

  • "Current position" is ViewerState.offset: an index into wrapped, i.e. a wrapped terminal row (src/viewer.rs:292-294). It changes meaning on resize, width override and l line-number toggle, because rebuild() re-wraps (src/viewer.rs:485).
  • Closest sibling: Backspace back-navigation via nav_history: Vec<(file_idx, offset)> (src/viewer.rs:365, 1765), pushed by dispatch_link (src/viewer.rs:1940). In-memory only.
  • The renderer already receives source byte ranges per event (src/markdown.rs:705, 1585), but Line does not keep them (src/style.rs:56).

Persistence

  • Only persisted thing is read-only config: Config::load() reads ~/.config/mdterm/config.toml, errors silently fall back to defaults (src/config.rs:29-43).
  • Nothing writes to disk today except task-checkbox toggling in the viewed file (src/viewer.rs:865).
  • dirs, serde, serde_json and toml are already dependencies (Cargo.toml).

Conflict: m is taken

  • m currently toggles mouse capture (src/viewer.rs:1647, help entry at src/viewer.rs:3637). Taking it for marks means rebinding mouse capture - question at the bottom.
  • ' is free in every mode.
  • Side finding: the m mouse toggle is missing from the README controls table (README.md:94-110) - worth fixing alongside.

Approaches

newmodifiedexisting, unchanged

A. Row marks in ViewerState, JSON file store not recommended

A mark is the wrapped-row offset at the time it was set. ViewerState holds a HashMap<char, usize> for the current file; a new marks.rs loads and saves a per-file map keyed by canonical path. Nothing below the viewer changes.

Benefits

  • Smallest change: viewer plus one new module.
  • Mirrors nav_history, which already stores raw offsets (src/viewer.rs:365).

Costs

  • Persistence is broken by design: a row index from an 80-col session points somewhere else in a 120-col session.
  • Within a session, resize or l silently moves every mark.
  • Fixing this later means a data migration of stored marks.

Touches

  • viewer.rs (keys, state, help)
  • new marks.rs, main.rs mod line

B. Source-anchored marks: lines carry their source line recommended

A mark stores the source line number of the top visible line. The markdown renderer stamps each Line with the source line of the event that produced it (it already has the byte range, src/markdown.rs:705); wrap_lines carries it onto every wrapped fragment. On jump, the viewer finds the first wrapped row whose source line is >= the mark. A new marks.rs owns the mark set and its persistence.

Benefits

  • Marks mean the same thing at any width, after resize, theme or line-number toggle, and across sessions.
  • Behaves like vim marks: edits above the mark shift it, edits below do not.
  • The source-line seam is reusable later (e.g. "open in $EDITOR at line", search-to-source).
  • Marks is pure data - unit-testable without a terminal.

Costs

  • Adds a field to Line, which has ~50 struct literals across markdown.rs, style.rs, json.rs, viewer.rs - mechanical but wide.
  • Source line is block/event granularity: a mark inside a long wrapped paragraph returns to the paragraph's first row.
  • JSON views have no meaningful source line, so marks are markdown-only (or row-based there).

Touches

  • style.rs (Line, wrap_lines)
  • markdown.rs (stamping), json.rs (literals)
  • viewer.rs, new marks.rs, main.rs

C. Heading-relative marks, no renderer change

A mark stores (heading slug, rows below heading), computed from the existing toc_entries (src/viewer.rs:661) and resolved with the same slug lookup as navigate_to_anchor (src/viewer.rs:1979). Falls back to document top when no heading precedes the mark or the heading is gone.

Benefits

  • No changes to Line, renderer or wrapping.
  • Survives edits in other sections, even reordering sections.
  • Reuses existing slug logic.

Costs

  • "Rows below heading" is still wrapped rows: drifts with width inside long sections.
  • Breaks on heading rename and on duplicate headings (first one wins, same as anchors today).
  • Documents without headings degrade to "top of file".
  • Two concepts (slug + rows) to explain and test.

Touches

  • viewer.rs, new marks.rs, main.rs

Shared by all approaches

  • New src/marks.rs, peer of config.rs, storing marks.json under dirs::data_dir()/mdterm/ (data, not config), keyed by canonicalized file path. Load/save errors degrade silently to "no marks" like Config::load (src/config.rs:30), with a toast on save failure.
  • The "waiting for a letter" step is a new ViewMode variant, matching how other multi-key flows are modeled (src/viewer.rs:230).
  • Jumping to a mark pushes onto nav_history so Backspace returns, like following a link (src/viewer.rs:1966).
  • Stdin input has no path, so marks there are session-only.

Recommendation

B. The feature's defining requirement is persistence between sessions, and only a width-independent anchor makes a persisted mark mean anything. A is wrong for that requirement, and C fixes it only partially while adding rename/duplicate edge cases. B's cost is a wide but mechanical change to Line, which per your guidance should not outweigh correctness, and it leaves a source-position seam the viewer currently lacks.
