Marks: m{a-z} to set, '{a-z} to jump, kept per file

Vim-style marks that keep pointing at the same content through terminal resizes, theme and line-number toggles, image loading and edits picked up by auto-reload. They persist across sessions in a small state file.

Today vs after

Today

  • m toggles mouse capture (src/viewer.rs:1647).
  • Scroll position is just state.offset, a row index into the wrapped output. It changes with width, gutter and image sizes.
  • Line has no link back to the source. The renderer reads into_offset_iter() (src/markdown.rs:1585) but throws the ranges away.
  • No per-file state is saved anywhere. Only config.toml is read.

After

  • m / ' are mark prefixes. M toggles the mouse.
  • Every row carries src, the source byte offset it came from, through wrapping and image expansion.
  • A mark is stored as {line, text} and found again by its text first, then by its line number.
  • marks.json lives in the state dir and is written atomically. It is never overwritten if unreadable.

How a mark travels

The question this answers: why do marks survive resizes and edits? They never store a row. Rows are turned into source offsets on the way in, and back into rows on the way out, against whatever the layout is at that moment.

style.rs · markdown.rs

Provenance

The rule: Line.src comes from the first span's event for text, the event start for borders, tables and images, a per-line offset in code blocks, and None for blank separators.

marks.rs (new)

Anchors + store

Pure functions over &str and &[Line], plus MarkStore. No terminal code, so all of it can be tested without a terminal.

viewer.rs

Wiring only

Prefix state, guards, toasts, status hint and help entries. No anchor logic lives here, which keeps the 4356-line file from growing a new concern.

Where the plan refines the spec

All four stay within the approved design's intent. They came from reading the renderer and test harness closely while planning.

Review focus: what's most likely to hit a real user

Inputs the spec implies but doesn't spell out as tests. Each now has a pinned test in the task that owns the code.

  1. Resize between set and jump. Set at 80 columns, shrink to 40, then jump: you land on the same block. Task 5 · mark_survives_resize
  2. Mark in a nested list or blockquote. The jump returns to the child item, not the parent or the start of the quote. Tasks 1, 5 · nested_list_item_gets_its_own_src, mark_on_nested_list_item_round_trips
  3. File shrinks under a mark during auto-reload. The jump clamps, doesn't panic, and shows (text not found). Task 5 · jump_after_truncation_clamps_and_reports_fallback
  4. Non-ASCII, CRLF and very long lines. Offsets inside a multibyte character don't panic, and lines over 256 characters still match after truncation. Task 3 · capture_handles_multibyte_and_crlf, long_line_fingerprint_still_matches
  5. Prefix followed by an unexpected key. A, 1, Esc, Ctrl+x and Alt+j cancel quietly without doing anything else. ' then q doesn't quit. Marks stay separate per file. Task 5 · prefix_then_non_letter_cancels_without_side_effects, marks_are_per_file

Risks and accepted trade-offs

Block granularity in prose. A mark set partway down a long wrapped paragraph jumps to the paragraph's first row. This was agreed in the design, because wrapped rows don't exist in the source.
About 55 mechanical src: None edits. They're spread across json.rs, style.rs and markdown.rs. The compiler finds every one, and the explicit field keeps provenance visible where each line is built.
Two instances writing the same mark at once. The last write wins for that one file and letter. Other entries are merged, so nothing else is lost. No file locking, by design.
Existing em dashes in the mouse toasts. The M arm moves the old body verbatim, including Mouse capture OFF — select text freely. Changing that copy is out of scope here. Say the word if you want it switched to - in the same task.

Pick an execution approach

recommended

Subagent-driven

A fresh implementer per task and a fresh reviewer gating each one, then a whole-branch review at the end.

Tasks 3-5 depend on exact signatures from earlier tasks (Line.src, Anchor, SaveStatus). A mistake in provenance would silently send every mark to the wrong place. Reviewing each task catches that early.

Native

One implementer works through all six tasks in this session, then one reviewer checks the whole branch.

Cheaper and faster. The plan carries the design, but nothing is independently reviewed until the end.
