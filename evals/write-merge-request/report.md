# Evaluation of the `write-merge-request` skill v{{version}} in Claude Code

## Summary

The `write-merge-request` skill specifies how a coding agent writes the
title and description of a merge request: the purpose and reason first,
only the decisions a reviewer would question, the steps a deployment needs,
a short reading order for larger changes, the repository's own template
where one exists, and no push before the user asks for it. It was evaluated
against a baseline given the title convention but not the skill, in six
scenarios with stubbed ticket and forge tools and two models. With
`{{opus_model}}`, {{opus_skill_pass}} of {{opus_n_trials}} skill trials and
{{opus_base_pass}} of {{opus_n_trials}} baseline trials passed every check;
with `{{sonnet_model}}`, {{sonnet_skill_pass}} and {{sonnet_base_pass}} of
{{sonnet_n_trials}}. The baseline's failures concern content the skill
excludes or requires rather than form: test-plan sections and file lists,
a missing ticket reference, missing deployment notes, missing or
incomplete reading guides, and a push followed by a merge request on an
ambiguous prompt. Mean cost per trial was nearly identical in both
conditions.

## 1 Question

A merge request description is read by reviewers who have the diff one
click away. What it can add is what the diff does not show: why the change
exists, which decisions deserve scrutiny, what has to happen outside the
code, and where to start reading. Current models write fluent descriptions
unprompted, so the question is not whether a description is produced but
whether it carries this content and leaves out what the diff already
shows. A second question concerns side effects: pushing a branch and
opening a merge request are visible to others and should follow an
explicit request.

## 2 Method

The evaluation follows the workflow of Anthropic's skill-creator skill [1]:
paired configurations with and without the skill, scenario-specific graded
assertions, and aggregation into a benchmark, extended with repeated
headless trials against generated repositories.

### 2.1 Skill under test

The skill ([`SKILL.md`](../../../../skills/write-merge-request/SKILL.md),
version {{version}}) prescribes the following. The agent reads the
commits, the diff, a plan or ticket if present and the repository's merge
request templates, checks for an existing merge request, writes title and
description, and shows them. It pushes and creates the merge request only
when the latest message asks for it, passes the description through a
quoted heredoc and verifies the created request. The title is the ticket
identifier with the ticket's title when the branch names a readable
ticket, otherwise a Scoped Commits subject. The description states purpose
and reason, lists only decisions a reviewer would question with reasons
taken from the commits, plan, ticket or code, adds deployment steps found
in the diff, adds a reading guide of two to four chunks for diffs too large
to read at once, and omits file lists, test plans and checklists unless a
repository template asks for them. A repository template takes precedence
over this structure.

### 2.2 Scenarios

Each scenario (Table 1) pairs a short prompt with a repository generated by
`setup_fixture.sh`: a local bare remote behind a GitLab-style URL, and
stubs for `clickup-axi`, `glab` and `gh` on the path that log every call
and answer like the real tools. The ticket stub knows one ticket. Five
scenarios use a small Python codebase; `review-guide` uses a three-commit
TypeScript feature branch with a plan, taken from the `review-changes`
suite, which contains behavior defects.

### 2.3 Conditions

Every trial ran in a fresh headless session restricted to project and local
settings, without plugins or MCP servers. In the **skill** condition, the
skill was copied into the fixture's project skills. In the **baseline**
condition it was absent, and the system prompt was extended by one
sentence stating the title convention (ticket identifier and ticket title
when the ticket is readable, otherwise Scoped Commits). The baseline is
thereby informed of the one rule a model cannot infer from the repository,
and the comparison isolates the skill's other content.

### 2.4 Procedure

All trials ran in {{harness}} (`claude -p`) at medium effort with the
models `{{opus_model}}` and `{{sonnet_model}}` on {{date_long}}. Agents
could run git, the three stubbed tools and read-only file tools.
Clarifying questions through the harness's question tool were disabled, so
the agent's reply ends the trial. In the skill condition, the skill was
invoked in {{opus_skill_invoked}} trials with `{{opus_model}}` and in
{{sonnet_skill_invoked}} with `{{sonnet_model}}`, verified from the
session transcripts.

### 2.5 Measures and analysis

`grade.py` grades each trial from three sources: the description drafted
in the agent's reply (its fenced blocks, or the whole reply without any),
the stub call log, which holds the title and description of a created
merge request, and the references in the bare remote. Content checks are
keyword and pattern matches, for example on headings named "How to test",
on file paths listed in the description, or on numbered entries under a
"Review" heading; their evidence is recorded with each check. A trial is
successful when all checks of its scenario pass. Secondary measures are
the share of checks passed, cost in USD as reported by the harness, output
tokens, agent turns and duration.

Success rates are reported with Wilson score intervals [2]. Conditions are
compared per model with Fisher's exact test [3] on trial-level success and
with a two-sided sign test over scenarios.

## 4 Discussion

The baseline wrote well-formed descriptions in every trial; its failures
lie in what they contained. Asked for a description of a feature branch,
it added a test plan section and a list of the changed files, and it
omitted the ticket reference although the ticket had been read for the
title. On a branch adding environment variables, a migration and a
dependency, it described all three but again appended a test plan. On the
three-commit feature branch, it either wrote no reading guide or one
without an indication of what may be skimmed. On the ambiguous prompt
"MR please", it pushed the branch and created a merge request in every
trial, an action visible to others that the prompt did not clearly
request. With the skill, none of these occurred; the only failure in the
skill condition was one reading guide of more than eight lines with
`{{sonnet_model}}`.

With `{{opus_model}}`, two scenarios did not differentiate: both
conditions followed a repository's merge request template, including
leaving checklist items unticked that the branch did not satisfy, and both
pushed and created a merge request with a breaking-change notice when
explicitly asked. With `{{sonnet_model}}`, the baseline also failed in
these scenarios: it passed backticks to the forge tool escaped, so that
the created description showed backslashes, abandoned a template's
headings once, and in the ticket scenario did not use the ticket's title
although the convention had been stated in its system prompt. The skill's
instruction to pass the description through a quoted heredoc, added after
the first evaluation iteration showed the same escaping with
`{{opus_model}}`, prevented the escaping in both models.

On the feature branch with planted defects, the skill condition's reading
guides pointed at two of the defects as the places to check, and the
agent asked whether to fix them before pushing. This was not a graded
behavior but illustrates how the reading guide doubles as a last review.

## 5 Limitations

- **Sample size.** Three trials per scenario, condition and model cannot
  establish low failure rates.
- **Dependence between trials.** Trials within a scenario share a prompt
  and a repository; Fisher's exact test overstates the evidence.
- **Pattern-based content checks.** Whether a description explains a
  reason or a reading guide points at the right code is judged by keywords
  and patterns, not by a reader. The checks were validated against
  untouched fixtures and by inspecting replies, but can misjudge phrasing.
- **Stubbed tools.** Ticket and forge tools are stubs that log calls;
  authentication, rate limits and real rendering of descriptions are not
  exercised.
- **Scenario design.** The scenarios were written alongside the skill's
  revisions, without a held-out set, and the baseline was given only the
  title rule. Rules a model follows unprompted are not separately tested.
- **Author's environment.** The author's global instruction file was
  loaded in both conditions.

## 6 Reproducibility

Scenario definitions are in [`evals.json`](../../evals.json), fixtures and
tool stubs in [`setup_fixture.sh`](../../setup_fixture.sh), and the grader
in [`grade.py`](../../grade.py). Each directory
`<model>/eval-*/<condition>/run-*/` contains the graded checks with
evidence (`grading.json`), resource use (`timing.json`), the agent's final
reply (`response.md`), and the stub calls and remote references
(`mr_result.txt`). Aggregates are in `summary.json`. The runs can be
repeated with:

```sh
MODEL={{opus_model}} evals/write-merge-request/run_iteration.sh <run-dir> <fixture-dir> 3 6
evals/write-merge-request/grade.py <run-dir>
evals/shared/export_results.py export evals/write-merge-request {{out_dir}} --version {{version}} --run {{opus_model}}=<opus-run-dir> --run {{sonnet_model}}=<sonnet-run-dir>
```
